## 3.9.0 (2026-11-10)

- **Claude Fable 5.2 joins the routing, sparingly** (owner, 2026-11-10: it doesn't replace Opus 5.5 as the main driver, since it costs more and uses up the subscription faster, and is used sparingly, for more demanding tasks only). Opus 5.5 stays the home model for the orchestrator and every task, even when the owner started the orchestrator on Fable. The contract chooses Fable per task, with its reason, like a level above extra high, and only for the more demanding work: hard design or architecture with no precedent where a wrong start costs hours, a problem Opus has already failed on, subtle correctness logic whose defects are costly. Never the default, never for helpers, reviewers, trial reviewers, fix-ups or follow-ups, never through OpenCode's per-request model, and only on a plan that includes it. Its effort is high, set explicitly since T3 and Claude Code default it to medium; extra high only with a named benefit; never max, low or medium, and no Ultracode on it unless the owner asks. Anthropic ranks Fable 5.2 a step above Opus 5.5, prices it at twice Opus's API rate, and still tells most work to start on Opus ([evidence.md](evidence.md#outside-sources)).
- **Its weekly limit is handled wherever usage is.** On plans that include Fable it may use up to half the weekly limits, inside the all-models week and faster than other models; `provider-usage` shows it as Claude's `weekly_fable` beside `weekly`. The contract names it beside the all-models week, judges a Fable task's capacity on both, and gives Fable work a budget of the Fable week (by default at most half of what is left); each wake's usage check compares it with the budget and its pace. A weekly limit can't be waited out like a 5-hour window, so when the Fable week runs out or passes its budget, a Fable task continues on Opus 5.5, at the same effort, on its own thread: the orchestrator sets the task's thread between turns (in T3, `t3_thread_configure` with the task's `threadId`, after interrupting its turn for a budget), never its own, and the ledger and report record the switch. It fits under "Quota pauses work; it never moves it" as the one model change, on the same subscription; a Fable task stopped by the all-models week or a 5-hour window still pauses. The rule reads each week's own reset time and treats the 5-hour window as for any Claude task, since Anthropic's pages don't say whether they differ.
- **`run-charts` draws the Fable week.** It skipped Claude's `weekly_fable`, because only keys ending in `weekly` or `monthly` counted as weekly windows; now a key that starts with one counts too, labelled "Fable weekly", a dashed line beside Claude's week, and in the usage line ("Claude weekly 20% → 18% left, Fable weekly 98% → 90% left"). It also stays, flat, when a task or helper label in the facts names Fable (not one billed by the API). `usage-sampler` already recorded it from its hourly live readings: the harness logs its 5-minute readings come from don't carry it, which its text and provider-usage's now say.
- The final report's usage line, the contract's usage paragraph and the owner's profile format (its Plans line, a preference and a calibration line) each have a place for the Fable week.
- **Ultracode is an option of its own in T3** (`{"id": "ultracode", "value": true}` beside the effort), not an effort value as routing.md said; T3's catalog lists it that way for Opus and Fable.
- **Review (Standard, by review-gate 3.0.0, for 3.8.1 and 3.9.0 together; Standard because they change rules live runs follow and two scripts they run, with no process control, deletion or outside input), 5 rounds:** blockers 0, 0, 0, 0, 0. Codex GPT-6.1 Terra found 12 follow-ups, all fixed: the run's Fable use is a running total kept in the ledger across wakes and weekly resets, with a wake 5 minutes before a reset, at least a point per Fable task for the unseen stretch, and the budget passed when no reading came in the reset's last 10 minutes; a missing, stale or reset-less Fable reading launches no Fable work and passes the budget after an hour (the reset-less case, from round 5, is fixed after the last round, unreviewed); Fable on the API instance has a dollar budget, not the Fable week; a Fable task's switch to Opus names what it left running and is sent only after a read-back shows Opus. ## 3.8.1 (2026-11-10)

- **A launch names the repository's T3 project when the orchestrator's thread is elsewhere** (owner's go-ahead, 2026-11-10, lesson L-93TA). Without `projectId`, `t3_thread_launch` makes the thread in the caller's project, so an orchestrator whose thread belonged to a project for a parent folder that isn't a git repository saw its whole first wave of nine launches fail at once ("Failed to resolve the VCS driver"), and nine failed threads had to be settled. host-t3.md's "Launch a task" now compares the thread's `projectId` with the integration checkout's project (`t3_project_list`, by `workspaceRoot`) before the first launch, passes it when they differ, and the launch example shows it.
- **A task's reviewers share one build folder, deleted after each round** (owner's go-ahead, 2026-11-10, lesson L-LM5V). The common file told each reviewer to build in a folder of its own under the task's scratch folder, so every reviewer made its own SwiftPM build of 3.5 to 7 GB: one task's scratch folder held 31 GB from six reviewers, and free disk fell 11 GB in five minutes and then 15 GB, until a rule added during the run stopped it. Now every reviewer of a task builds into `<run directory>/<task ID>/scratch/review-build` (`swift build --scratch-path` or the like) or doesn't build, and the task deletes it once each review round is over.
- **`lease` refuses `--all` on the cpu** (owner's go-ahead, 2026-11-10, lesson L-MU4E). One task re-ran its full check with `lease run cpu --all` to pass a timing test and held all three build slots for about 20 minutes while six tasks waited. Now `lease acquire` and `lease run` with `--all` on the cpu exit 2 with a message naming the one-slot rule, take nothing and run nothing, unless the cpu's entry in `leases.json` sets `"all_ok": true`; `--all` on every other resource, such as the whole GPU for a timing run, works as before. machine.md and the task brief's lease rule say a timing run takes one cpu slot like any build. SwiftPM locks its build folder, so reviewers sharing one wait for each other, and the brief says to build one at a time with a tool that doesn't lock (review follow-up).
- **Review:** with 3.9.0, below.

## 3.8.0 (2026-11-07)

- **A merged task's harness temp folders are removed too** (owner, 2026-11-07). Claude Code keeps a temporary folder for each working folder its sessions ran in, `${CLAUDE_CODE_TMPDIR:-/tmp}/claude-<uid>/<the path, non-alphanumerics as "-">/<session>/`, with the session's scratchpad and background-task output; it outlives the worktree and nothing cleans it. One run's 24 task worktrees had left 52.6 GB there (one task 32.6 GB of evaluation libraries, model copies and builds) after its cleanup removed every worktree and `scratch/` folder and its report called every temporary folder cleaned up; the owner noticed free disk falling from 189.5 to 125.7 GB over the runs. Now `scripts/prune-runs --harness-temp <worktree> <run directory>/<task ID>` lists those folders with their sizes, a path's by its exact name (over 200 characters, cut there with Claude Code's own hash) and, for a task's folder, those of its `scratch/` and the folders inside that, never a sibling task's such as `S4-fix`'s for `S4`, and removes them with `--apply` (nothing when a task folder named holds `KEEP`), never through a link and never the home folder's or a run's own. The cleanup after a merge runs it once the worktree is gone; the finish lists what is left for every task; `--size` adds a second line counting them, for the report's closing line; and the common file tells tasks that their harness's temporary or scratchpad folder isn't a scratch folder and to list anything over 100 MB left outside theirs, and to tell the reviewers and helpers they start to build into the task's scratch folder or not at all: in the same run, after this rule, a merged task's worktree folder still held 6.6 GB, two reviewer sessions' SwiftPM builds of 3.3 GB each. Removing the worktree's whole folder, every session in it, catches those too. Codex, OpenCode and Antigravity keep logs and state in their own folders, not a folder per worktree, so they are left alone.
- **`run-watch`'s disk line names the folder that grows** (same lesson): when free disk falls 10 GB in 5 minutes or drops below 20 GB, it sizes the running tasks' worktrees, task folders and the Claude Code temp folders of both with `du`, within 20 seconds in all, and names the one that grew most since a disk line last sized them, or else the largest.
- **A cpu slot is a share of the cores** (owner's go-ahead, 2026-11-07, lesson L-2UKE). `lease run cpu` starts its command at low priority (nice 10) and caps its parallel jobs at cores ÷ slots, or the resource's `jobs`: `MAKEFLAGS`, `CARGO_BUILD_JOBS` and `CMAKE_BUILD_PARALLEL_LEVEL` when the command doesn't set them, and a `swift` wrapper first on its PATH that adds `--jobs` to `swift build`, `test` and `run` unless they name it; a nested `lease run cpu` doesn't lower it again. A cpu with `slots_while_owner_here` gives a new acquire only that many slots while the owner is at the computer (input within `owner_here_seconds`, 300 by default, or an idle time that can't be read; a locked screen counts as away), and machine.md says to set it one below `slots` in an evening run. In one evening run eight tasks with three full-speed Swift builds took the load to about 100 on 18 cores while the owner used the computer, and the harness was restarted twice; the same two changes made by hand brought it to about 20.
- **Exact times are kept, not just printed** (owner's go-ahead, 2026-11-07, lesson L-DN4A). `run-watch` adds its `commit`, `merged` and `report` lines to `<run directory>/times.log`, and the ledger takes its times from there or from the integration branch's `git reflog --date=iso`, never from memory. It printed each time only on the first wake after it, and a busy wake that skimmed its output lost them: ledger times written from memory still ran 5 to 12 minutes late.
- **Review (Deep, by review-gate 3.0.0; raised from the brief's Standard because prune-runs deletes folders outside the run and lease changes how commands start), 5 rounds:** blockers 3, 1, 1, 0, 0. Round 1 (Codex GPT-6.1 Terra, Claude Sonnet 5.5, OpenCode DeepSeek V4.1 Flash free, Claude Haiku 5.5 trial) found that a task folder's prefix match took a sibling task's temp folder (`S4-fix` for `S4`) and that a long name matched any folder sharing its first 200 characters; now names are exact, a long one by Claude Code's own hash, and only a task's `scratch/` is searched below it. Rounds 2 to 5 (Terra; Sonnet in round 2) narrowed what is under `scratch/`: a name another folder or watch.json task of the run could also own, or one another existing folder encodes to (`/a/task-b` and `/a/task/b`), stays and is named, and an unreadable inventory takes nothing. Also fixed: `KEEP` honoured, the swift wrapper's per-process temp name, times retried when `times.log` can't be written, run-watch sizing the real path's and scratch sessions' folders and re-sizing a low disk every 10 minutes at most, and the finish naming the task's folder. Round 5's two follow-ups (a watch.json that isn't an object, `--size` counting the kept folders) are fixed with tests after the last round. Left: two different paths that encode alike when neither still exists (Claude Code's own naming), scratch paths over 200 characters, and `hold()` retaking all slots of an `--all` lease that ran out while the owner is there.

## 3.7.0 (2026-11-06)

- **Every wake starts with `scripts/run-watch`** (owner, 2026-11-06, lesson L-JCEF). It reads files and processes only, no model and no network, takes a few seconds, and prints one line per finding and nothing when all is well: a running task's tool call open over 6 minutes whose processes used no CPU or GPU, started nothing and wrote nothing for 6 minutes (a hang, with its process IDs and the kill that stops them); a shell call with no process at all (an approval prompt); a task whose session log, worktree and run folder haven't changed for 20 minutes; a process not the run's above 80% of a core for 10 minutes; free disk falling 10 GB in 5 minutes or below 20 GB, swap above 20 GB, a password dialog, a stopped keep-awake or sampler; and the exact times of each task's commits, merges and report-backs, for the ledger. A call's processes are those started with it and what they started, so another call's busy server hides nothing, and a lease is a wait only until it holds its turn: then its command is judged. `hang` needs proof, not an average: under half a second of CPU since a sample at least 6 minutes old, or in the process's whole life, and no kill is offered when another call started within a minute of it. Idle isn't proof a call is stuck, so the orchestrator stops a hung call only when it can name what the call waits on and why that won't answer: a read of a pipe whose other end only the harness holds (`lsof -p <pid> -d 0,1,2`), or a stack parked in a wait the run already knows stalls (`sample <pid> 1`, which ran without a prompt on the task's own processes); otherwise it tells the task what looks stuck. This refines L-JCEF's "stop what hangs" at the review (making sure it hangs), rather than adding a rule: both of the run's hangs pass it, a stray `cat` parked in `read` and an evaluation in a semaphore wait. A call idle now that isn't shown idle all that time, or holds a network connection, gets an `idle` line, a look rather than a kill, and `hang` on a later wake once it is shown idle; one still idle after 20 minutes is called probably stuck. It reads Claude Code and Codex session logs, and says once for each running task whose log it can't read (another harness, or a log not found) that it sees only that task's processes and files. In one run two hangs inside running tasks, a stray command reading stdin and an evaluation stuck at 0% CPU, were found only because the orchestrator read the task's session log and process tree on its own, a check the skill didn't contain; a system service pinned a core and stalled three tasks' tests for about an hour before a task's report mentioned it; and ledger times written from memory were wrong three times. Of the run's 17 tool calls of 5 minutes or more only one or two were stalls, so the age of a call alone isn't enough: reviewer waits, lease queues, benchmarks and sleep loops on background jobs are told apart by their CPU, GPU, new processes and files.
- **`watch.json` in the run directory** says what to watch: Prepare writes the run's start, the integration checkout and the keep-awake's and sampler's process IDs, each launch adds the task's worktree, harness, session or thread, branch and launch time, and a task that stops running gets its status. The host references say how each host's task log is found: in T3, from the `--session-id` (or `--resume`) T3 gives a Claude Code task's `claude`, since the thread's own data doesn't carry it; on Claude Code, the subagent's log under the orchestrator's session; for Codex, the rollout that names the worktree.
- **Known limit:** a Codex `exec_command` that yields a session ID and keeps running leaves the open-call check when its call returns, so a stall after that is seen only by the 20-minute quiet check. Fixing it needs Codex's record of the session's end, which no local rollout showed.
- T3's heartbeat prompt runs it first, and the Claude Code and Codex wakes start with it. `tests/run-watch-test` covers the two hangs, an approval wait, a call moved to the background on its timeout, a Codex task, and the benign long calls, with CPU use made up so the test burns no core.
- **Review (Standard, by review-gate 3.0.0), 4 rounds and a fix-up look, all Codex GPT-6.1 Terra:** blockers 3, 1, 1, 2, so the gate stopped at round 4. Found and fixed: a quiet healthy call could be killed on a short or averaged CPU look (now `hang` needs proof and anything less is `idle`); `lease run` hid a stuck command; processes were tied to the task, not the call; a missing Codex subagent log was silent; an idle call with a network connection never escalated; a failed `lsof` read as "no connection"; frequent wakes dropped the sample that proves idleness. The open blocker, that idleness isn't proof a call is stuck, was settled by the orchestrator's decision to stop only on named evidence (above); the fix-up look at that wording and the retention fix found no blocker, and its two follow-ups (a parked stack or a pipe alone doesn't show nobody will answer) are fixed in the wording.

## 3.6.0 (2026-11-06)

- **A stopped task with known fixes gets a fresh fix-up agent** (owner, 2026-11-06). When no follow-up path fits a stopped review, or its fresh look stops it, and the task names a concrete fix for each open blocker without doubting its approach, a new agent continues on the same branch and worktree with a new context (in T3, a thread on the existing worktree): it applies the fixes with tests, gets one more look by the cross reviewer and merges. At most two fix-ups per task; only a disputed approach, a product decision, a blocker with no concrete fix or a third stop waits for the owner. The brief lists them, the orchestrator sends the next one to the same thread once one merges, each report names its milestone (`milestone=1/3`), and a dependent may start once the milestone it needs merges. In the same run each app part, 2 to 5 thousand changed lines, was reviewed as one diff at the end, and one stop held back a whole feature, so the owner woke to a placeholder.
