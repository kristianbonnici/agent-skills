## 5.10.3 (2026-11-19)

- **A prune of older runs never overlaps a round starting or finishing in that folder** (5.9.2's open follow-up, from its review: a new round could start on the other computer while an approved `prune-runs --apply` there was planning its removals). The run's lock, `<root>/.<run>.lock` beside the run folder, is held by `prune-runs` from its check of a run.json-only run through its last removal (a run whose lock is held is passed by), by `--mark-finished`, and by the new `prune-runs --mark-running <run directory> --orchestrator <computer>`, which the pre-flight on the other computer now runs first, before it writes anything else there, to write `run.json` afresh with the round's `started` time. `--mark-finished` needs that time back (`--started`), so a finish retried after a new round began marks nothing. `--mark-running` takes only an empty folder or one holding its `run.json`; a populated one without it needs `--adopt`. Both marks work through the folder opened without following a link once the lock is held, wait up to ten minutes for a prune to end (an 11-minute timeout for the call), then exit 75: run them again. A dry run takes no lock. The lock file is checked to be the one at its path once taken, so one removed or replaced meanwhile is taken again. Copies before 5.9.2 never prune a folder without its ledger, and 5.9.2 reaches `main` only with 5.10.3, so every copy that can prune one takes the lock.
- **Two timestamp hardenings for such a run** (the same review): `--mark-finished` writes `"finished"` to the microsecond, and a file in the folder counts as changed after the finish with no allowance (5.9.2 allowed five seconds); the age now counts from the latest of that time and run.json's modification and change times, so a marker put back with `cp -p` is young again. The activity check walks the folder only once the age has passed.

## 5.10.2 (2026-11-19)

- **Another computer's one-time lines survive a lost result** (5.10.0's open follow-up 1). `run-watch --as` keeps each one-time line (a hog, a blind task, a first VM or leftover line, a sleep, a commit or report, a fall of the disk) pending there with an ID, and sends it with every result until the next `watch.json` the orchestrator's `run-watch` sends there names it in `"ack"`, which it does only once a result carrying it has arrived (a `watch.json` with no `"ack"`, from an older orchestrator or a hand run, gets every line in `"lines"` as before, so a 5.10.0 orchestrator loses nothing either); so a connection dropped after the result went out loses no line, and none is printed twice. The orchestrator keeps what each computer last delivered across a wake that checks none (an unreadable `watch.json`); the other computer keeps the newest 300 pending lines, and says so in a `note` when older ones go unread.
- **The other computer's time limit stops what a hung command started too** (follow-up 2): in `--as` mode each command (`ps`, `lsof`, `pmset`, `git`, `du`, …) runs in a session of its own with no input, and a timeout or the limit kills its whole process group and reaps it, not only the command itself.
- **A reading the other computer can't take is "unknown", never a number** (follow-up 4): a failed `sysctl` there sends swap as null rather than 0.0, a load it can't read the same, and the heartbeat shows `disk unknown`, `swap unknown` or `load unknown` for any number that didn't arrive or couldn't be read, as it does for the keep-awake and the sampler.
- **The heartbeat names every computer it should have checked** (follow-up 5): it lists the computers `watch.json`'s `"machines"` reaches over SSH (never its own, which it names as `run-watch` does when `watch.json` leaves out `"computer"`), so a first wake whose `run-watch` fails before saving anything still says `den-mac not checked this wake`.
- Still open from 5.10.0, for later: overlapping heartbeats share the state's blind list (and its acks, so two at once can print a one-time line twice); a worktree path followed by a space can match a longer path; times beyond the 200 KB replay window aren't added.
