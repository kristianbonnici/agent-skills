# Source rationale

Last checked: new work 2026-11-06; sources 2026-09-18.

This skill is an original synthesis, not a vendored copy of a course or upstream skill. It adds no runtime dependencies. The sources below inform decisions; they do not override the target project's requirements or authorize actions.

## Course foundation

[WalkingLabs: Learn Harness Engineering](https://walkinglabs.github.io/learn-harness-engineering/en/) and its [harness-creator skill](https://github.com/walkinglabs/learn-harness-engineering/tree/77e7a3e21469dcbece2558086c8d91657abeaa40/skills/harness-creator).

Inspected repository revision: `77e7a3e21469dcbece2558086c8d91657abeaa40`.

All 14 English lesson bodies at this revision were read end-to-end for this revision of the skill, including their examples, diagrams as source, caveats, and exercises. The advanced repository pack and its SOPs, initializer/startup playbooks, and selected state/bootstrap/handoff templates were also reviewed. Reading the exercises is not a claim that every course project was executed. See [lesson coverage](lesson-coverage.md) for the specific implementation of each lesson's contribution.

Treat its examples as context-specific proposals. Do not import mandatory filenames, feature counts, instruction line budgets, performance estimates, stack templates, or cleanup commands. In particular, making a handoff clean does not authorize reverting local configuration or user changes. Verify claims about products and performance against primary sources before relying on them.

## Primary engineering sources

| Source and publication date | Practical contribution | Limit on generalization |
|---|---|---|
| [OpenAI: Harness engineering](https://openai.com/index/harness-engineering/), 2026-02-11 | Discoverable repository knowledge, concise entry instructions, executable boundaries, runtime visibility, and continuous maintenance. | A report from a particular internal product and workflow; its directory structure, autonomy, and merge policy are not universal requirements. |
| [Anthropic: Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), 2025-11-26 | Separate initial setup from subsequent work; retain task state and verification evidence for later sessions. | Specific application-building experiments; neither their file formats nor their feature-list size is a baseline for every repository. |
| [Anthropic: Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps), 2026-03-24 | Evaluate actual outcomes and reconsider scaffolding as capabilities change. | Evaluators, sprint structure, and context resets have conditional value; extra agents are not an unconditional reliability guarantee. |
| [Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), 2025-09-29 | Select relevant context and disclose detail progressively; use durable notes when they support continuity. | Broad engineering guidance, not evidence that every new instruction improves task performance. |
| [Anthropic: The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory), Lance Martin, 2026-11-06 | Keep what loads into every session small ("the top layer of the memory hierarchy has to stay relatively small"), with an index that points to deeper notes, and record what the code or environment doesn't already show. Carrying a memory folder between fresh sessions raised CL-Bench 1.0 mean reward from 0.655 to 0.838 for Opus 5.5 and from 0.644 to 0.833 for Sonnet 5.5. In Pokémon Red, Sonnet 3.7 kept 413 files, often one per battle, item or character met, also wrote down what the screen already showed (money, map position), and its "detailed record was continuously going out of date"; it earned one badge. Fable 5 kept nine files of "things the game didn't explicitly tell it" and earned four. | About notes an agent writes for itself, not instruction files people keep for a repository. Gives no size threshold for what loads every session. Mostly single figures per condition with no variance reported, and one Pokémon run per model, comparing Sonnet 3.7, several generations back, with Fable 5. |
| [Anthropic: The new rules of context engineering for Claude 5 generation models](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/), Thariq Shihipar, 2026-07-24 | Claude Code's team "removed over 80% of Claude Code's system prompt for models like Claude Opus 5 and Claude Fable 5" with "no measurable loss on our coding evaluations". They had been overconstraining it, "both through our system prompt" and "in our CLAUDE.md files and skills": constraints once needed to avoid worst cases, such as deleting files, could give way to the model's own judgement from context. → *Remove demonstrably stale or duplicate guidance; ask whether the environment still earns its maintenance cost.* | The team's own product and unpublished evaluations, with no figure per removed rule; the cut was to a host's system prompt, not a repository's instruction file. It does not support removing what only the project knows: accepted decisions and non-obvious constraints. |
| [Anthropic: Reducing cost and improving performance with Claude Platform](https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform), Lance Martin, 2026-09-08, re-run after Opus 5.5's launch on 2026-09-22 | "Prompts can accumulate instructions that patch model weaknesses", and "these instructions can drift relative to the capabilities of the latest Claude models". Names the patterns: verification rituals, thoroughness and emphasis boosters, mandatory procedures and scratchpad scaffolds, stale examples, contradictory rules, and dated configuration. Migrating a customer-support benchmark from Opus 4.8 to Opus 5.5, removing them cut cost "by an additional 9%", and accuracy "rose by around 2 percentage points". → *Remove demonstrably stale or duplicate guidance; the Maintenance row's duplicate rules and abandoned scaffolding.* | One benchmark of an API application's prompts, not repository instruction files. The post traces the accuracy gain to three specific problems (a retired thinking setting, contradictory refund rules and a manual scratchpad), not to shorter instructions in general. |
| [AGENTS.md open format](https://agents.md/), reviewed 2026-09-18 | A widely supported Markdown convention for repository-specific agent guidance. | Actual discovery, precedence, imports, and nested-file behavior depend on the host; verify them before proposing host-specific integration. |
| [Matklad: ARCHITECTURE.md](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html), 2021-02-06 | A concise physical code map, important boundaries, invariants, and cross-cutting concerns. | Prefer stable relationships over exhaustive inventories; adapt to the repository's existing documentation conventions. |
| [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents), 2024-12-19 | Simple composable workflows, environmental feedback, explicit stopping conditions, and conditional use of evaluators. | Framework choices and product features change; added orchestration must justify its cost. |
| [LangGraph: Persistence](https://docs.langchain.com/oss/python/langgraph/persistence), reviewed 2026-09-18 | Checkpoints identify recoverable workflow state and separate executions. | Persistent state alone is not a guarantee that replayed external side effects occur exactly once; no LangGraph dependency is introduced. |

## Empirical counterweights

- [Gloaguen et al., Evaluating AGENTS.md](https://arxiv.org/abs/2602.11988v3), ETH Zurich, version 3, 2026-09-29 (abstract unchanged from version 2 of 2026-06-23); preprint, presented at the ICLR 2026 Workshop on Memory for LLM-Based Agentic Systems (a workshop, not a main track), per the [authors' publication page](https://www.sri.inf.ethz.ch/publications/gloaguen2026agentsmd); it stays cited as a preprint from an established group, not for its venue: context files did not generally improve task success in the evaluated settings and increased average inference cost. The authors distinguish useful non-standard practices from unhelpful repository overviews. This supports selective instructions and testing their effects, not banning instruction files.
- [Lulla et al., On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents](https://arxiv.org/abs/2601.20404v2), version 2, 2026-03-30: a study of 10 repositories and 124 pull requests associated context files with lower median runtime and output-token consumption, with comparable completion behavior. This supports measuring efficiency as well as outcomes, not promising a universal speedup.
- [He et al., Acquiring and Verifying Repository Norms for Coding Agents](https://arxiv.org/abs/2610.07757), Sun Yat-sen University and Singapore Management University, 2026-10-06, preprint: "Changes produced by coding agents can pass functional tests while leaving repository contribution requirements unmet." Supplying norms extracted and checked against repository evidence, across three coding models and 121 tasks, raised overall norm compliance by 7.42–10.77% (relative) over no added guidance and beat generated documentation (CodeWiki) for every model; functional success rose 5.79–9.09 points, short of significance. This supports instructions that state non-obvious, checkable project constraints rather than general overviews, and a passing test suite not being taken as proof that a change meets the project's rules. → *Use repository-specific instructions for non-obvious constraints; treat passing evidence as specific to what was tested.*
- [Zhang et al., Rethinking Verification in Agent Harnesses](https://arxiv.org/abs/2610.34577), Cornell University and Alibaba Group, 2026-10-25, preprint: 17 verification designs across seven frontier coding models on Terminal-Bench and SWE-bench Verified. Initial instructions and mid-turn reminders gave "modest, model-dependent average gains"; completion gates "can yield larger gains but may substantially increase cost"; independent review by a critic improved accuracy by 5.9–9.5 points on Terminal-Bench and 3.9–6.6 on SWE-bench at 1.13–1.25× and 1.00–1.04× baseline cost. Only "6.2–13.6% of detected editing turns are followed by a recognized checking command before the next editing turn or the end of the run". This supports treating written rules as advisory unless a check enforces them, and scaling verification to the failure modes rather than adding prose. → *Written rules are advisory unless a checker or runner enforces them; scale verification to the change.*
- [Mohsin et al., Teaching Agents to Code Reliably](https://arxiv.org/abs/2610.03984), AWS AI Labs and Stanford University, 2026-10-02, preprint (submitted to ICLR 2027): on SWE-bench Verified, "a test the agent writes for its own patch accepts many incorrect ones"; the authors' reinforcement objective, which trains the verifier against incorrect variants, "lifts verifier precision from 26.8% to 41.7%". This supports verification evidence that does not rest on checks the agent wrote for its own change alone. → *Treat passing evidence as specific to the tested code; do not weaken existing checks or completion criteria to claim improvement.*

These studies use different settings and measures. Do not combine their results into a single expected improvement. None settles the value of a particular project's instruction file. Correctness, time, and token cost remain separate observations.

## Updating this guidance

Revisit a source when a proposed change depends on a newer claim or a host's changed behavior. Record the reviewed revision or publication version and date. Keep only source details that explain a skill decision. Do not automatically synchronize upstream content or copy a growing catalog of practices into the entrypoint.

## Left out

Weighed and not cited, so later checks don't weigh them again unless they change:

- [Khatri, Do Context Files Help Coding Agents? A Two-Agent Ablation Study on Real Repositories](https://arxiv.org/abs/2607.27250), 2026-07-28: bears on the context-file rules (no measurable correctness effect over 288 runs), but a single-author preprint.
- [Zarzycki, What Open-Source Projects Tell Their Coding Agents: A Census of AGENTS.md and CLAUDE.md](https://arxiv.org/abs/2610.31715), version 2, 2026-10-26: bears on what instruction files contain (74.0% of directives give no reason), but a single-author preprint without a named affiliation.
- [Anthropic: Redesigning source control at Anthropic](https://www.anthropic.com/research/redesigning-source-control), 2026-10-13: first-party, but about version-control infrastructure at agent scale; bears on no rule of this skill.
- [GitHub: Building Git infrastructure for agent-scale development](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/), 2026-10-06 (updated 2026-10-26): first-party, but about hosting infrastructure load; bears on no rule of this skill.
- [Anthropic: Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), reviewed 2026-11-14: "Prefer general instructions over prescriptive steps"; product documentation with no method or figures.
- [OpenAI: Reasoning best practices](https://developers.openai.com/api/docs/guides/reasoning-best-practices), reviewed 2026-11-14: prompting reasoning models to "think step by step" is "unnecessary"; product documentation with no method or figures, about API prompts.
- [Claude Code: Audit your instruction files](https://code.claude.com/docs/en/memory), reviewed 2026-11-14: a host check for "instructions written for older models" that proposes edits; a host feature, not a study, and no rule of this skill depends on it.
