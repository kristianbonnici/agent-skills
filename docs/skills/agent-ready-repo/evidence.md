| [Anthropic: Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps), 2026-03-24 | Evaluate actual outcomes and reconsider scaffolding as capabilities change. | Evaluators, sprint structure, and context resets have conditional value; extra agents are not an unconditional reliability guarantee. |
| [Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), 2025-09-29 | Select relevant context and disclose detail progressively; use durable notes when they support continuity. | Broad engineering guidance, not evidence that every new instruction improves task performance. |
| [Anthropic: The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory), Lance Martin, 2026-11-06 | Keep what loads into every session small ("the top layer of the memory hierarchy has to stay relatively small"), with an index that points to deeper notes, and record what the code or environment doesn't already show. Carrying a memory folder between fresh sessions raised CL-Bench 1.0 mean reward from 0.655 to 0.838 for Opus 5.5 and from 0.644 to 0.833 for Sonnet 5.5. In Pokémon Red, Sonnet 3.7 wrote "413 memory files across 225 folders", often one per battle, item or character met, also wrote down what the screen already showed (money, map position), and its "detailed record was continuously going out of date"; it earned one badge. Fable 5 kept ten files (nine in two folders plus a top-level `global.md`) of "things the game didn't explicitly tell it" and earned four. | About notes an agent writes for itself, not instruction files people keep for a repository. Gives no size threshold for what loads every session. Mostly single figures per condition with no variance reported, and one Pokémon run per model, comparing Sonnet 3.7, several generations back, with Fable 5. |
| [Anthropic: The new rules of context engineering for Claude 5 generation models](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/), Thariq Shihipar, 2026-07-24 | Claude Code's team "removed over 80% of Claude Code's system prompt for models like Claude Opus 5 and Claude Fable 5" with "no measurable loss on our coding evaluations". They had been overconstraining it, "both through our system prompt" and "in our CLAUDE.md files and skills": constraints once needed to avoid worst cases, such as deleting files, could give way to the model's own judgement from context. → *Remove demonstrably stale or duplicate guidance; ask whether the environment still earns its maintenance cost.* | The team's own product and its own coding evaluations, with no figure per removed rule. The 80% cut was to a host's system prompt; for CLAUDE.md files and skills the post reports overconstraint but gives no figure. It does not support removing what only the project knows: accepted decisions and non-obvious constraints. |
| [Anthropic: Reducing cost and improving performance with Claude Platform](https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform), Lance Martin, 2026-09-08, re-run after Opus 5.5's launch on 2026-09-22 | "Prompts can accumulate instructions that patch model weaknesses", and "these instructions can drift relative to the capabilities of the latest Claude models". Names the patterns: verification rituals, thoroughness and emphasis boosters, mandatory procedures and scratchpad scaffolds, stale examples, contradictory rules, and dated configuration. Migrating a customer-support benchmark from Opus 4.8 to Opus 5.5, removing them cut cost "by an additional 9%", and accuracy "rose by around 2 percentage points". → *Remove demonstrably stale or duplicate guidance; the Maintenance row's duplicate rules and abandoned scaffolding.* | One customer-support benchmark of API prompts, not repository instruction files: the post started from a clean prompt and planted one anti-pattern in each of six, and the 9% is the average across the six, not an audit of a real application. It traces the accuracy gain to three specific problems (a retired thinking setting, contradictory refund rules and a manual scratchpad), not to shorter instructions in general. |
| [Anthropic: How the Claude Code team thinks about verification](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/), Addy Osmani, 2026-11-16 | On the team, "the vast majority of our code (~90%) is written and reviewed by Claude", and checks, not instructions, hold it: "If a change can modify the check that judges it, the check is broken"; code review reads REVIEW.md "from the base or default branch, never from the pull request's changes"; a commit gate "can block a commit if the session did not contain /code-review or /verify"; a 39-item reliability checklist where each item has "a trigger that can be read from a diff", so only those that match run, "usually 3 to 10". "Test suites, verification steps and .md files only grow if you let them, so we tidy them up on a routine." A separate grader checking against a rubric "improved task success by up to 10 points". → *Written rules are advisory unless a checker or runner enforces them; do not weaken existing checks or completion criteria; scale verification to the change; remove demonstrably stale or duplicate guidance.* | The team's own practice. The one outcome figure (up to 10 points) comes from internal testing on structured file generation, with no task count or model. It also says a CLAUDE.md rule "(mostly)" stops a repeated issue, so it does not claim prose never works. |
| [AGENTS.md open format](https://agents.md/), reviewed 2026-11-20; now "stewarded by the Agentic AI Foundation under the Linux Foundation" | A widely supported Markdown convention for repository-specific agent guidance. | Actual discovery, precedence, imports, and nested-file behavior depend on the host; verify them before proposing host-specific integration. |
| [Matklad: ARCHITECTURE.md](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html), 2021-02-06; a design source, kept as still the standard reference on its point | A concise physical code map, important boundaries, invariants, and cross-cutting concerns. | Prefer stable relationships over exhaustive inventories; adapt to the repository's existing documentation conventions. |
| [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents), 2024-12-19; now notes that "Much of the tooling landscape described in this post has changed since December 2024"; kept as the standard reference for its design principles, which the note leaves standing | Simple composable workflows, environmental feedback, explicit stopping conditions, and conditional use of evaluators. | Framework choices and product features change; added orchestration must justify its cost. |

## Empirical counterweights

- [Gloaguen et al., Evaluating AGENTS.md](https://arxiv.org/abs/2602.11988v3), ETH Zurich, version 3, 2026-09-29 (still current on 2026-11-20; dated: its agents ran Sonnet 4.5, GPT-5.2, GPT-5.1 mini and Qwen3-30b-coder, two or more generations back, and nothing newer repeats its task-success measurement) (abstract unchanged from version 2 of 2026-06-23); preprint, presented at the ICLR 2026 Workshop on Memory for LLM-Based Agentic Systems (a workshop, not a main track), per the [authors' publication page](https://www.sri.inf.ethz.ch/publications/gloaguen2026agentsmd); it stays cited as a preprint from an established group, not for its venue: context files did not generally improve task success in the evaluated settings and increased average inference cost. The authors distinguish useful non-standard practices from unhelpful repository overviews. This supports selective instructions and testing their effects, not banning instruction files.
- [Lulla et al., On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents](https://arxiv.org/abs/2601.20404v2), version 2, 2026-03-30; preprint, listed for the Journal Ahead Workshop (JAWs) 2026, a workshop, and kept as a preprint from an established group (dated: one model, gpt-5.2-codex): a study of 10 repositories and 124 pull requests associated context files with lower median runtime and output-token consumption, with comparable completion behavior. This supports measuring efficiency as well as outcomes, not promising a universal speedup.
- [He et al., Acquiring and Verifying Repository Norms for Coding Agents](https://arxiv.org/abs/2610.07757), Sun Yat-sen University and Singapore Management University, 2026-10-06, preprint: "Changes produced by coding agents can pass functional tests while leaving repository contribution requirements unmet." Supplying norms extracted and checked against repository evidence, across three coding models and 121 tasks, raised overall norm compliance (with three small models: DeepSeek V4 Flash, Qwen 3.5 Flash and Gemini 3.1 Flash-Lite) by 7.42–10.77% (relative) over no added guidance and beat generated documentation (CodeWiki) for every model; functional success rose 5.79–9.09 points, short of significance. This supports instructions that state non-obvious, checkable project constraints rather than general overviews, and a passing test suite not being taken as proof that a change meets the project's rules. → *Use repository-specific instructions for non-obvious constraints; treat passing evidence as specific to what was tested.*
- [Zhang et al., Rethinking Verification in Agent Harnesses](https://arxiv.org/abs/2610.34577), Cornell University and Alibaba Group, 2026-10-25, preprint: 17 verification designs across seven frontier coding models (all open-weight: Qwen, GLM, DeepSeek, Kimi and MiniMax; no Claude or GPT) on Terminal-Bench and SWE-bench Verified. Initial instructions and mid-turn reminders gave "modest, model-dependent average gains"; completion gates "can yield larger gains but may substantially increase cost"; independent review by a critic improved accuracy by 5.9–9.5 points on Terminal-Bench and 3.9–6.6 on SWE-bench at 1.13–1.25× and 1.00–1.04× baseline cost. Only "6.2–13.6% of detected editing turns are followed by a recognized checking command before the next editing turn or the end of the run". This supports treating written rules as advisory unless a check enforces them, and scaling verification to the failure modes rather than adding prose. → *Written rules are advisory unless a checker or runner enforces them; scale verification to the change.*
- [Mohsin et al., Teaching Agents to Code Reliably](https://arxiv.org/abs/2610.03984), AWS AI Labs and Stanford University, 2026-10-02, preprint (submitted to ICLR 2027): on SWE-bench Verified, "a test the agent writes for its own patch accepts many incorrect ones"; the authors' reinforcement objective, which trains the verifier against incorrect variants, "lifts verifier precision from 26.8% to 41.7%". This supports verification evidence that does not rest on checks the agent wrote for its own change alone. → *Treat passing evidence as specific to the tested code; do not weaken existing checks or completion criteria to claim improvement.*

- [Voria, Kashiwa, Catolino and Palomba, Do They Do as They Are Told? Investigating Coding Agents' Adherence to Explicit Instructions in Context Files](https://arxiv.org/abs/2611.13709), University of Salerno and Nara Institute of Science and Technology, 2026-11-10, preprint: 268 repositories, 621 context-file snapshots and 6,541 commits by Copilot, Claude Code and OpenAI Codex, each instruction turned into a script that checks the commits. "The mean per-instruction compliance rate is 59.8%, but the median is 100.0%", a "strongly bimodal distribution": of 2,053 instructions, 54.4% were always followed and 37.3% never; development-process instructions complied least among the categories with enough instructions to compare (mean 34.0%). The authors conclude that context files are "one layer of governance, not sufficient on their own", and that conventions may be better encoded "directly into project tooling". Observational (it never sees what an agent does without an instruction), only 67 of 94 sampled checking scripts (71.3%) were judged correct, its counts differ between sections, and the models behind the commits are not given. → *Written rules are advisory unless a checker or runner enforces them; use repository-specific instructions for non-obvious constraints and reliable commands.*

These studies use different settings and measures. Do not combine their results into a single expected improvement. None settles the value of a particular project's instruction file. Correctness, time, and token cost remain separate observations.

## Updating this guidance

Revisit a source when a proposed change depends on a newer claim or a host's changed behavior. Record the reviewed revision or publication version and date. Keep only source details that explain a skill decision. Do not automatically synchronize upstream content or copy a growing catalog of practices into the entrypoint.
