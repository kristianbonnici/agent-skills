# Routing and capacity

Each task needs a provider and model. Route tasks across the owner's peer primary subscriptions by live capacity and model fit, and keep small subscriptions to the helper and strength roles they were sized for.

## 1. Peer primary subscriptions and home harness

The home harness is the harness and model the orchestrator itself runs on:
- **T3:** `inheritedProviderInstanceId` and `inheritedModel` from `orchestrator_capabilities`.
- **Plain Claude Code:** Claude.
- **Plain Codex:** Codex.

The owner's profile names the run's **peer primary subscriptions** (Claude Max 20x and Antigravity Ultra ($200)). "Home harness first" is relaxed between them: a run's contract may place tasks on either peer primary subscription by live capacity and model fit — for example, a Claude orchestrator running most tasks on Antigravity Gemini models when Claude's week is tight, or an Antigravity orchestrator routing highest-stakes logic or architecture tasks to Claude Opus:

- **Claude (`claudeAgent`):** `claude-opus-5-5` for highest-stakes logic/architecture or when Claude Max has room; Fable 5.2 stays rare, chosen for a task only with a reason ([Fable 5.2](#fable-52-the-demanding-tasks-only)).
- **Antigravity (`antigravity`):** plain `gemini-4-neon` (`thought_level: "high"`, or `"xhigh"` with a named benefit) for all Antigravity primary tasks. Never use `gemini-pro-orchestrator-neon` (Orchestrator (Neon)): it hands most turns to Hydrogen and breaks the prompt cache on model switches without a real cost win.

If you yourself run on one of OpenCode's free or Go models, don't treat it as a primary harness for complex tasks: route those to the primary subscriptions (Claude Max 20x or Antigravity Ultra) unless the contract routes a specific lane to Codex under its small-plan rules below. Small subscriptions (such as ChatGPT Plus, OpenCode Go, and GitHub Copilot) remain non-primary and never absorb primary tasks; a task goes there only when:
1. **Strength:** another provider clearly does a particular piece of work better and has room for it (section 4, such as Codex computer use on Terra).
2. **The user asked**, in the request or the contract (including whole tasks explicitly placed in the free/Go pool).

**Your own thread never switches provider or model during a run.** Tasks stay on their assigned subscription across short 5-hour resets (pausing and resuming in place), while weekly limits or run weekly budgets may spill queued or running tasks between peer primary subscriptions as section 3 says.

## Reasoning level: medium for bounded work, high for demanding work

Medium is the normal level for a well-specified, bounded task; high is for demanding work. An under-powered agent on demanding work still costs more than it saves (wrong turns, rework, failures found in the morning), so when a task is both, take high:

| The work | Reasoning level |
|---|---|
| A well-specified, bounded task: documents, small fixes, mechanical changes, settings, an integration with a clear spec | medium |
| Demanding work: design judgment, a tricky bug, data and sync, a broad review | high |
| Antigravity primary task (plain `gemini-4-neon`; never `gemini-pro-orchestrator-neon`) | high (`thought_level: "high"`; `"xhigh"` only with a named benefit in the contract) |
| A task where you see a real benefit from extra thinking (for example subtle correctness or security logic, a bug with an unknown cause, a design choice with no precedent in the project). Name the benefit in the contract | extra high (never on Antigravity Claude, which does not expose `xhigh`) |
| Rarely, on Claude: a task where Opus 5.5 would probably fall short and Fable would clearly do better. Name why in the contract | Fable 5.2 at high, not Opus 5.5 ([Fable 5.2](#fable-52-the-demanding-tasks-only)) |
| Sparingly: large or many-sided work that clearly gains from parallel sub-agents inside the task (several independent lanes, a broad review, a big refactor). Name the gain in the contract, and the brief's lane cap: "at most <n> sub-agents at once, <m> in all", from the contract's budget for it | the harness's multi-agent mode: Ultracode in Claude Code, Ultra in Codex |
| A fast helper's step or research lane, on Antigravity or OpenCode | high (see "Fast helpers" below) |
| An advanced helper step, on Gemini 4 Neon | high: `gemini-4-neon` with `thought_level: "high"` (`gemini-4-neon-high` in `agy`; see "Advanced helpers" below) |

- **Never use low reasoning.** If a task feels too small for medium, it is probably a step to hand off, not a task.
- **Always set the level explicitly at launch,** and never inherit a model's default. Some defaults are low or medium: in T3, Codex's `gpt-6.2-sol`, `gpt-6.1-sol` and `gpt-6.1-terra` default to low, and Antigravity's Claude models default to medium.
- **In T3, the option names differ by provider:**
  - Claude (`claudeAgent`): `{"id": "effort", "value": "medium" | "high" | "xhigh"}`. Ultracode is an option of its own beside it, `{"id": "ultracode", "value": true}`, only on models that list it, such as Opus and Fable, not Sonnet. Claude's models default to medium in T3, so always pass the effort.
  - Codex (`codex`): `{"id": "reasoningEffort", "value": "medium" | "high" | "xhigh" | "ultra"}`.
  - Antigravity (`antigravity`): `{"id": "thought_level", "value": "medium" | "high" | "xhigh"}` on Gemini models (`gemini-4-hydrogen`, `gemini-4-neon`, `gemini-3.8-flash`), and `{"id": "thought_level", "value": "high"}` (never `"xhigh"`, which the catalog does not expose) on Antigravity Claude (`claude-opus-5-5`, `claude-sonnet-5-5`). The `-high` / `-xhigh` names in this file are `agy`'s, where the level is part of the name.

  Use only values the capability catalog lists for that model.
- **Capacity still applies.** Higher reasoning uses more of a subscription, and the multi-agent modes use a 5-hour window much faster than a single agent, because every sub-agent draws on the same window. Start a multi-agent task early in a window, not when the window is already well used, and expect it to pause for a reset on a long run. Don't step down to a level below what the work needs to save capacity.
- **A budget is set before the call, not after.** A wake can't stop a call already running: four multi-agent tasks with 10 to 97 sub-agent lanes each have taken 16 points of Claude's week in about 16 minutes, and one async lane on Gemini 4 Argon once took 80 points of its week against a budget of 30. So a multi-agent task's brief names its lane cap, and Neon as an advanced helper inside non-Neon tasks runs one call at a time, within the count of calls its brief names ([Advanced helpers](#advanced-helpers-gemini-4-neon)).

## Fable 5.2: the demanding tasks only

Claude Fable 5.2 (`claude-fable-5-2`) is a step above Opus 5.5, and it costs about twice as much: twice Opus's price per token on the API, and on a subscription it uses up the week faster than other models, within a weekly limit of its own. The owner wants it used very sparingly. So:

- **The answer is Opus 5.5 (or plain `gemini-4-neon` on Gemini-routed tasks), complex tasks included.** Opus 5.5 is the standard model for Claude work in section 1, alongside plain `gemini-4-neon` for Antigravity primary work. Hard, long, important or many-sided Claude work is still Opus work.
- **Fable only when the contract can say why Opus would probably fall short and Fable would clearly do better:** "Fable 5.2 at high, because <why Opus would probably fall short here>". The usual case is a problem Opus 5.5 has already failed on: a bug whose cause two attempts didn't find, a review that stopped twice on the same design question (a relaunch, with the contract's or the owner's yes). Most runs have no Fable task.
- **For the part that needs it.** A Fable task's later milestones, and any fix-up agent, follow-up task, helper or reviewer, run on Opus 5.5 (the `review-gate` skill's tables never use Fable), unless the contract says why that part needs Fable too.
- **Not for your own thread, unless the owner set it.** Don't move yourself to Fable; if the owner started you on it, stay on it (never switch your own model during a run), and say in the contract what your wakes will cost of the Fable week (measured once at about a point every 15 to 20 minutes with no Fable task running) so they can switch your thread to Opus before they leave.
- **Only on the Claude provider** (`claudeAgent`). Never through OpenCode's `opencode/claude-fable-5-2`, a paid model that bills per request. On the API instance it draws on the credits, about twice as fast as Opus, and not on the Fable week: there the credits' rules and reserve hold it ([Claude API credits](#claude-api-credits-use-what-would-expire)), the contract gives it a budget in dollars of its own, and the Fable week's budget and checks below don't apply.
- **On the subscription, only on a plan that includes it.** On plans where Fable isn't part of the usage limits it bills usage credits from the first token: the profile's Plans line says which, and a live `provider-usage` reading with `weekly_fable` is the sign it is included. Without that, no task runs on Fable on the subscription; a task on the API instance needs only its dollar budget and the credits' reserve.
- **Effort:** high, set explicitly (T3 and Claude Code default Fable to medium). Extra high only with a benefit named in the contract, for the hardest long-running work. Never max, low or medium, and no Ultracode on Fable unless the owner asks for it: every sub-agent would draw on the same Fable week.

### Its weekly limit

`provider-usage` shows Claude's Fable week as `weekly_fable`, read from Claude Code's `/usage` ("Current week (Fable)") beside `weekly`, the week for all models. It is read live only: the harness logs that `--cached` and the sampler's 5-minute readings come from don't carry it, so the sampler records it with its hourly live readings, and a usage check for it runs `provider-usage` live.

- **Fable work counts on both weeks.** It draws on the all-models week, faster than other models, and the Fable week is a cap inside that week, not extra room. Read each one's `resets_at` rather than assuming they reset together. Whether Fable counts toward the 5-hour window more heavily isn't published: judge a Fable task's 5-hour window as any Claude task's.
- **Capacity is judged on both.** A Fable task fits only when the Fable week has room for it within the run's budget and the all-models week still has room for the rest of the run with it. Until the profile has a calibration for Fable, assume a Fable task-hour takes about twice an Opus task-hour of the all-models week.
- **The contract gives Fable work a budget** in points of the Fable week: by default at most a quarter of what is left, so the owner keeps the rest of their week, and less when the all-models week is short. Name the Fable tasks and their reasons, and record the budget, and the Fable week's reading at the start, in the ledger.
- **Every wake's usage check watches it** while a Fable task runs: compare what the run has used of the Fable week with the budget, and watch the pace as for a 5-hour window (section 3). When the budget will be passed before your next heartbeat at the current pace, treat it as passed.
  - **What the run has used** is a running total kept in the ledger beside the last reading it counted: each wake adds the rise since that reading. When the week has reset since (`resets_at` passed, or `reset_since_observed`), it adds the new reading whole, and for the stretch between the last reading before the reset and the reset, the use at the run's average Fable pace (its total so far over the Fable task time so far), and never less than one point for each Fable task that ran in it. So that stretch stays short, a Fable task running when the Fable week will reset gets a one-off wake about 5 minutes before its `resets_at`, scheduled like a resume wake, which takes that last reading: check that the wake's next run falls before the reset, and when the reset is less than 10 minutes away, take the reading now instead. When no reading came in the last 10 minutes before the reset, the run's budget counts as passed. A reset doesn't refill the run's budget.
  - **A missing reading is no reading.** A live `provider-usage` without `weekly_fable` (the live call failed and the logs it falls back to don't carry it) or with a stale `observed_at` or no `resets_at` (so a reset can't be told from use) can't show the budget: launch no Fable work on it, and when no fresh reading has come for an hour while a Fable task runs, treat the budget as passed.

### When the Fable week runs out or passes its budget

A weekly limit can't be waited out like a 5-hour window, and Opus 5.5 is on the same subscription, so the task moves model instead of pausing. This model move keeps the task on the same Claude subscription; peer-primary weekly spillover is separate ([A weekly limit](#a-weekly-limit)):

1. **The Fable task continues on Opus 5.5, at the same effort, on its own thread.** In T3, once its turn has stopped (the Fable limit stops it; for the budget, `t3_thread_interrupt` its turn and wait until the thread is idle), look for what it started that may still run in its worktree, its background jobs and the reviewers or helpers it launched, as the cleanup after a merge does ([integration.md](integration.md#cleanup-after-a-merge), steps 2 and 3; in T3 also its child threads, `t3_thread_list` with `includeSubagents: true`), and name them in the message below so the task waits for them or stops them first; then set its thread's model between turns: `t3_thread_configure` with the task's `threadId` and a `modelSelection` of `claude-opus-5-5` with its effort ([host-t3.md](host-t3.md#when-a-window-runs-out)), never your own thread, as the last call of your wake. On the next wake, read it back, then send: "Your model is now Claude Opus 5.5, because the run's Fable budget is used up. <Still running from before: …; check them before you change files.> <Your review-gate and helper wakes were deleted: set a new review-gate wake while a reviewer still runs, and a new helper wake while an async helper you wait on still runs, each with its next wake number.> Continue the brief from where you stopped." It keeps its whole conversation. Where a host can't set a running agent's model (a Claude Code subagent), save its uncommitted work as a patch and continue it with a continuation brief on Opus 5.5 in its worktree ([task-brief.md](task-brief.md#continuation-brief)).
2. **The ledger records the switch:** the time, the task, the Fable week's reading against the budget, and why. Launch no more Fable work in this run, and the report names the move.
3. **A Fable task stopped by the all-models week or the 5-hour window:** on the 5-hour window it pauses like any other task (Opus draws on the same window); if the all-models week runs out or passes its budget while Antigravity Ultra has ample room, see [A weekly limit](#a-weekly-limit).

### A Fable second opinion for your own decisions

**Fable 5.2 (`claude-fable-5-2` on `claudeAgent`) is the ONLY orchestrator second-opinion model.** Never substitute Gemini, Codex, or another model. An orchestrator running on another primary harness (such as Antigravity) still calls Fable 5.2 on `claudeAgent` subject to the same Fable and Claude budget/window checks below (never through Antigravity's `claude_and_gpt_models` bucket and never through OpenCode's `opencode/claude-fable-5-2`). A few of your decisions shape the whole run; before those, ask Fable 5.2 one bounded question with the facts it needs, answered once, not Fable running the run. Fable doesn't see your conversation, only the brief you write, so a call costs what that brief and the files it reads cost.

**When:** only at these points, and only where the answer is a real choice:
- **The contract,** before you post it: the split into tasks, the waves and dependencies, the routing, the review levels, and anything you were unsure about.
- **A review that didn't converge,** before the task waits for the owner ([integration.md](integration.md#a-review-that-didnt-converge)): whether the approach itself is wrong, and a concrete fix for each open blocker if it isn't.
- **A blocked or failed task whose cause isn't mechanical,** before you park it or relaunch it: what is wrong and what the next attempt should do differently.

Never for a review of a diff (the review gate does that, and Fable never reviews), never for routine wakes, and not when your own thread runs on Fable.

**The brief,** self-contained: the decision and its options; the facts (the contract draft, or the task's brief, handoff and open findings, with the worktree path and branch for it to read); what you lean towards and why; and what to return: a recommendation, its reasons, what would change it, and its confidence. Tell it to stay read-only, not to commit, run nothing that writes or may ask for approval (if it stops on a pending approval: cancel it with task_cancel and ask once more, then decide without it), not to reach the owner's apps or services, and never to ask the user anything.

**How:** in T3, `delegate_task` with target `{providerInstanceId: "claudeAgent", model: "claude-fable-5-2", options: [{id: "effort", value: "high"}]}`, role `"research"`, `interactionMode: "plan"` (Claude's read-only mode), mode `"async"`: its completion wakes you. `delegate_task`'s mode `"wait"` returns after at most about 45 seconds, and a wait that times out doesn't stop the child, so set the wake below before you launch it. In Claude Code, the `Agent` tool with `subagent_type: "Plan"` (read-only: no edit or write tools; only the brief keeps its shell read-only), `model: "fable"` and `effort: "high"`, in the foreground. In Codex, a command with a time limit: `perl -e 'alarm 900; exec @ARGV' claude -p --model claude-fable-5-2 --effort high --permission-mode plan "<brief>"`, from the worktree when there is one. Not through the API instance unless the contract gives it a dollar budget, and never OpenCode's `opencode/claude-fable-5-2`.

**Its budget:** the contract allows at most 3 second opinions by default (the contract's own, and two later), and always states a Fable budget in points of the Fable week, with the reading it started from, even when no task runs on Fable: then the budget is for the opinions alone, by default 5 points or a quarter of what is left, whichever is less. The contract's own opinion comes before that approval, so take it only while the Fable week has at least 10 points left, and count what it used in the budget the contract states. Take a live reading before each one and after it, of both `weekly_fable` and `weekly`. Each reading updates the run's Fable and Claude totals as a wake's reading does, from the last reading counted ([Its weekly limit](#its-weekly-limit), [The run's Claude estimate and budget](#the-runs-claude-estimate-and-budget)), so other work running meanwhile is counted once and the opinion isn't counted twice. Record both readings in the ledger. Calibrate opinions per call, not per hour (the 20-minute rule below is for tasks): note in the ledger the rise on each week of an opinion that ran while no other Claude work did, a rise shared with other work as shared, and one whose week reset between its readings (`resets_at` passed) as not measured. Put a per-opinion figure in the profile only from at least three such opinions, as their average, across runs. Skip it, and decide alone as before, when the count is used, the run's Fable total has reached its budget or would before the opinion ends at its pace, a live reading is missing, the owner's Claude plan doesn't include Fable, or the run's Claude budget or a Claude window has no room for it ([The run's Claude estimate and budget](#the-runs-claude-estimate-and-budget)).

**When it doesn't answer in time:** give it about 15 minutes, judged from its thread's `createdAt` (`t3_thread_read`), never from how many waits returned. Its completion wakes you only if it finishes, and a `t3_thread_wait` on it may return early or tell you to end your turn, so in T3, before you launch it, set a wake that doesn't depend on it, unless one is set (a relaunch after an approval keeps it): `schedule_task({title: "<run> second-opinion wake", schedule: {type: "interval", everyMs: 300000}, bindToCurrentThread: true, clientRequestId: "<run>-second-opinion-wake-<k>", prompt: "Second-opinion wake for run <run>. If the opinion was already handled (the ledger says so, or before the contract is approved, this thread), or the run is paused, stopped or finished, delete this scheduled task and end the turn with one line. Otherwise check the Fable opinion you wait on as routing.md says: a pending approval, and its 15 minutes from createdAt. If it has answered or been stopped, take its answer and after-reading, go on with the decision, record it in the ledger once there is one, and delete this scheduled task."})` (<k> counts the second-opinion wakes set in this run, kept in the ledger once there is one: a wake set again after a failed launch takes the next), with its ID in the ledger once there is one. Delete it once the opinion has answered or been stopped and you have taken it, or at once if the launch fails. On each wake and each early return, check its thread for a pending approval and its time. Past its 15 minutes, cancel it (`task_cancel`), check that `task_status` shows it stopped, and only then take the after-reading and decide alone. It counts against the 3. On Claude Code, a foreground `Agent` call ends with its answer or its error; on Codex, the time limit above stops the command.

**You still decide.** It advises; your rules still say what waits for the owner. Weigh its answer against what you know, and record in the ledger's decisions log the question, its answer in a line, your decision, and whether its answer changed it. A concrete fix it names counts as the task naming one ([integration.md](integration.md#a-review-that-didnt-converge)) once the task agrees the fix fits, never for a product decision or a disputed approach, which still wait for the owner. The report says how many second opinions the run asked for and what they changed.

## 2. Measure capacity as plan size times room left

Run `scripts/provider-usage` (in this skill's folder):
- at the start;
- before each wave;
- on every wake while any active primary subscription's 5-hour window is past about half (passing `--only antigravity` live when Antigravity runs or is past ~50%);
- at the finish.

It prints each provider's plan and the usage and reset time of its 5-hour and weekly windows. Record each snapshot in the ledger.

The script asks each provider directly, so the numbers include use from other devices and apps (claude.ai, ChatGPT, Codex elsewhere):
- **Claude:** Claude Code's own `/usage` command, run without a model call (`claude -p /usage`). It uses no quota and works even when the window is used up. Its windows are `five_hour`, `weekly` (all models) and, on plans that include Fable, `weekly_fable`, Fable's own week inside it ([Fable 5.2](#its-weekly-limit)).
- **Codex:** Codex's app server (`account/rateLimits/read`), with Codex's own sign-in.
- **Antigravity:** the Antigravity CLI's own `/usage` command (`agy -p /usage`), which starts no agent turn and uses no quota. Antigravity splits its models into groups, and each group has its own windows:
  - `gemini_models_five_hour` and `gemini_models_weekly`: every Gemini model, so Antigravity primary tasks (`gemini-4-neon`), the review gate's Neon `xhigh` and Hydrogen Light reviews, Neon advanced helpers, and Hydrogen fast helpers all draw on this one pair. On the owner's Ultra plan the group holds Gemini 4 Neon, Carbon, Argon and Hydrogen, the Orchestrator models and Gemini 3.8 Flash (the group's note in the snapshot lists them);
  - `gemini_4_argon_weekly`: on the Pro plan only, Argon's own week. The run no longer uses Argon;
  - `claude_and_gpt_models_five_hour` and `claude_and_gpt_models_weekly`: Antigravity's separate Claude and GPT quota bucket. **Primary use:** Claude Opus 5.5 and Sonnet 5.5 reviews (`thought_level: "high"`, `interactionMode: "plan"`) under `review-gate` while every reported `claude_and_gpt_models_*` window is under about 80%, sparing Claude Max — especially for Gemini-authored changes and whenever Claude Max's week is tight (e.g. past ~65%); fails over seamlessly with `claudeAgent` in both directions. **Secondary use:** optional bounded Claude tasks (`claude-opus-5-5` or `claude-sonnet-5-5`, `thought_level: "high"`, never `xhigh`, which the catalog does not expose on Antigravity Claude) when Claude Max is tight and `claude_and_gpt_models_*` has ample calibrated room, with a weekly budget of its own in the contract and `watch.json`'s `usage_marks`. **Never use `GPT-OSS 120B`** for reviews or primary coding tasks.

  Quota is used in proportion to the cost of the tokens, so a call's size matters more than how many calls there are. If `ai_credits_remaining` appears, the owner has paid credits that Antigravity can spend once a window is used up. Never let a run spend them: an Antigravity task or helper that reports a quota error stops there, even if credits would let it go on.
- **Copilot:** GitHub's own quota endpoint (`gh api /copilot_internal/user`, the one its editors use), which spends nothing. Copilot has one window, `monthly`, with `units_entitled` and `units_remaining`; it resets on the first of the month. It is billed by token cost in fractional units, not per request. If the live read fails, `local_units_used_this_month` gives what this machine's Copilot sessions spent (from `~/.copilot/session-state`), but not what is left. If `overage_permitted` appears, GitHub would bill the owner past the budget: never let a run go past it.
- **OpenCode Go:** the endpoint T3 Code reads (`opencode.ai/zen/go/v1/usage`), with the key OpenCode keeps for its console, which spends nothing. All Go models show as one set of windows, `five_hour`, `weekly` and `monthly`, in whole percents. The endpoint isn't documented, so if it stops answering, watch Go's helpers for errors instead. It is left out without an OpenCode key, and shows an `error` when OpenCode refuses the key.

When a live query fails, for example with no network, the script falls back to the last values Claude and Codex wrote to local logs and says so in `source`. Antigravity and OpenCode Go have no such logs, so they get an `error` instead. Those are only as fresh as the last request made on this machine. `--cached` skips the live queries; `--go-live` beside it still reads OpenCode Go, one web request and no tokens, as the usage sampler does.

Codex may list free rate-limit resets (`reset_credits_available`). Never use one: spending them is the user's decision.

Percentages from different plans are not comparable. 30% left of Claude Max 20x is many times more work than 30% left of ChatGPT Plus. Turn each number into how many tasks still fit:

```
tasks that fit ≈ (100 − used_percent) / percent one task uses on that plan
```

- **Where "percent one task uses" comes from:** the calibration in the user's profile (section 6). With no calibration yet, be conservative on small plans. On a Plus-sized plan, assume one heavy implementation task takes about a whole 5-hour window per hour of work (about 90% of a window per task-hour). On a Max-sized plan, assume a small share.
- **Learning it:** after each task, update the calibration from the snapshots taken before and after. If several tasks shared the provider, split the change between them by duration. Calibrate only from real runs, with tasks of about 20 minutes or longer. Short tasks and test runs give wildly misleading per-hour rates: a 3-minute task that moves a window by 3 points is not "60% per hour". When a run is too short to calibrate from, say so in the ledger and leave the profile unchanged.
- **The 5-hour window limits a wave; the weekly window limits the whole run.** The weekly window also covers the user's next days, so don't plan to use more than about 80% of a weekly window without saying so in the contract.
- **Staleness:** treat `observed_at` as the age of the number. A window with `reset_since_observed: true` has reset since it was read, so it is near zero again.
- **Missing data:** if a provider's usage can't be read, say so and route by plan size alone. The usage of OpenCode's free tier is never readable, so its helpers are watched for errors and slowdowns instead (section 4). Watch Antigravity's helpers that way too whenever its usage can't be read.
- **Other runs share the windows.** Another orchestrator run on the same machine draws on the same subscriptions. Before the contract and before each wave, look for other ledgers next to yours:

  ```sh
  grep -l -E '^Status: (running|paused)' "${XDG_STATE_HOME:-$HOME/.local/state}"/agent-skills/long-horizon-orchestrator/*.md
  ```

  A ledger without a `Status:` line (from an older version of this skill) is active too while any branch its task rows name still has a worktree (`git worktree list`), whatever its age. For each active run, count its running tasks on each provider and leave room for them. Name them in the contract, and in the report's usage line, because they make the usage numbers a shared total. Then coordinate with it, as below.

### The run's Claude estimate and budget

Estimate the run's Claude use from its own tasks, never from an earlier run's total: more tasks at once, or tasks on Fable, use the week many times faster. Count:
- each Claude task's expected hours by model, at the profile's calibration (points of the all-models week per task-hour), or without one about one point per Opus task-hour and two per Fable task-hour on a Max 20x plan;
- their reviews and fix-ups on Claude, by each task's review level;
- your own wakes, twice as much on Fable;
- the Fable second opinions the contract allows: by the profile's calibration, or else about a point of the all-models week each, with what the contract's own one used on both weeks ([A Fable second opinion](#a-fable-second-opinion-for-your-own-decisions)).

Say the estimate in points of the all-models week, and give the run a Claude budget in those points: by default the estimate plus a quarter, and never more than the owner's share of what is left. The ledger keeps what the run has used as a running total, counted as the Fable budget's is ([Fable 5.2](#its-weekly-limit)), and every wake's usage check compares it with the budget. When the run would pass it before the next heartbeat at its pace, launch no more Claude work:
- if peer-primary spillover is enabled and Antigravity Ultra has ample room ([A weekly limit](#a-weekly-limit)), route queued and unstarted Claude tasks there (and hand off an interrupted running task at most once via the clean handoff path if stopped for the budget while still far from finished);
- otherwise, park later milestones and unstarted Claude tasks (`parked`) for the owner, let running tasks finish what little remains before stopping (or park them cleanly if substantial work remains), and record the state in the ledger and report.

### The run's Antigravity budgets

When a run uses Antigravity (primary Gemini tasks, Neon reviews, Neon advanced helpers, Hydrogen fast helpers/reviews, Antigravity Claude reviews, or bounded Antigravity Claude tasks), track its two weekly buckets separately in the contract, ledger, and `watch.json`'s `"usage_marks"`:

- **`antigravity.gemini_models_weekly`:** covers Antigravity primary tasks (plain `gemini-4-neon`), Neon `xhigh` reviews, Neon advanced helpers, and Hydrogen helpers and Light reviews. Always use the owner's profile calibration once populated; until then, owner-approved initial Ultra $200 estimates put `gemini-4-neon` primary tasks at ~0.5 points of `gemini_models_weekly` per task-hour and plain Neon `xhigh` reviews at ~0.2–0.3 points per round (Hydrogen is negligible).
- **`antigravity.claude_and_gpt_models_weekly`:** covers Antigravity Claude review rounds (`review-gate` while every reported `claude_and_gpt_models_*` window is under ~80% and the run's weekly budget has room) and any optional bounded Antigravity Claude tasks (`claude-opus-5-5` or `claude-sonnet-5-5`, `thought_level: "high"`). Owner-approved initial Ultra $200 estimates put an Antigravity Sonnet 5.5 `high` review round at ~0.8 points weekly (~1.15 points 5h) and an Antigravity Opus 5.5 `high` review round at ~3 points weekly (~6 points 5h), so the bucket absorbs many reviews comfortably while full Opus coding tasks should be budgeted conservatively until calibrated on full tasks.
- **`watch.json` `"usage_marks"` and live reads:** `scripts/heartbeat` holds one numeric threshold per `"<provider>.<window>"` key in `watch.json`'s `"usage_marks"` and prints `": its budget is used"` whenever `used >= mark` (for cap and soft-reserve marks without a run budget, that suffix still means only that the configured threshold was reached). Store only the **single lowest threshold not yet acted on** per key — e.g. weekly budgets, active 5-hour limits not named `five_hour` (`"antigravity.gemini_models_five_hour": 85`, `"antigravity.claude_and_gpt_models_five_hour": 80`), and review-gate caps (`"codex.five_hour": 60`, `"codex.weekly": 70`, stepped to `85`/`80` while `Codex is reserved for Deep` is active; `min(budget, 80)` on `"claude.weekly"` and `"antigravity.claude_and_gpt_models_weekly"`). Once you act on a crossed mark, advance it to the next threshold or remove that key (e.g. `budget -> 80 -> remove`, Codex `60/70 -> 85/80 -> remove` when `Codex is short`, resetting on window resets) so the next threshold mark is armed (`heartbeat` suppresses repeated unchanged warnings after first delivery and tracks built-in `>= 95%` independently so an active mark never masks the first `>= 95%` crossing). Drop any separate `95` mark so `heartbeat`'s built-in `>= 95%` warning fires automatically. Because `usage-sampler` reads Antigravity live only once an hour (Antigravity has no cached local log) and `heartbeat` auto-flags 85% only for windows named `five_hour`, pass `--live` to `scripts/heartbeat <run directory> --live` while Antigravity tasks or heavy Antigravity reviews run or when an Antigravity 5-hour window passed ~50% on the last reading, and run `scripts/provider-usage --only antigravity` live before each wave. Never take the idle early-exit while any `common.md` flag is active and recovered below threshold on the usage line (then confirm the recovery live before withdrawing the flag).

### Running beside another orchestrator

The owner sometimes runs two orchestrators at once on one computer, often on the same repository, or tells one to start after another.

- **Told to start after another run: wait at no cost.** Schedule no heartbeat or repeating wake, prepare nothing that holds resources (keep-awake, sampler, leases, worktrees), and end your turn. Before that, make sure the run ahead knows your thread: tell its orchestrator thread once with `t3_thread_send` (mode `queue`: your run, thread, repository, and what your first wave needs of the screen or GPU), unless the owner already told it. Set at most one `once` wake, as a backup in case that run dies: at its estimated end plus a few hours. Its start message (below) wakes you; then prepare and coordinate as the rest of this section says.
- **Another run waits to start after yours:** record it in `watch.json` as `"next_run": {"thread", "environmentId" (another computer's), "repo", "needs": ["screen", "gpu"] (what its first wave needs), "leases": "<the shared lease folder>"}`. `run-watch` prints `next-run` once nothing of yours is queued or paused and the tasks still running are none in its repository and hold no lease it needs (when it can't tell, or nothing runs, it waits for the finish), and at the finish whatever runs. On that line, send its thread the start message: the versions of this skill and `review-gate` to use, the shared lease folder, and what of yours still runs, with its code areas. Record it in the ledger and set `"started"` in `"next_run"`, so the line stops. Then the two runs coordinate as below.

When another run is active:

1. **Write to it before your contract.** Its ledger names its thread (in T3, send to that thread with `t3_thread_send` in mode `queue`). Say which run you are, where your ledger is, which code areas and shared resources your tasks will use, your ports and folders, and when you expect to finish. Wait about 5 minutes for its answer, judged from when you sent it (in T3, `t3_thread_wait` on its thread; after each return, read its last message, and stop once it has answered; while it hasn't, wait again only while its thread runs, since a wait on an idle thread returns at once, and once it is idle without an answer go on as below; if a wait tells you to end your turn first, set a wake for that time before you end it: `schedule_task` with `schedule: {type: "once", runAt: "<the send time plus 5 minutes, in UTC>"}`, `bindToCurrentThread: true` and a prompt that names the other run's thread and says to read its answer and go on with the contract, check that its `nextRunAt` is that time, and delete it once it has fired). Keep the note and its answer in your ledger, and ask it to keep them in its own. If no answer comes (the run is paused, or doesn't know this protocol), go on with safe defaults, however old its ledger (a run that seems dead may still have tasks working, so never treat it as gone): stay out of the code areas its ledger names, use its lease folder if it has one (otherwise make one and tell it), keep clear of its ports and folders, and leave the shared finish to whichever run turns out to be last.
2. **Split the code areas.** Say in your contract which parts of the code your tasks stay out of because the other run works there, and ask it to do the same for yours. Overlap only where both runs agree.
3. **Share one lease folder.** Both runs take turns at the screen and the GPU through the same leases: a folder of its own next to the ledgers (for example `<repo>-<computer>-leases/`, with `bin/lease` and `leases.json`, [machine.md](machine.md#6-shared-resources-and-disk)), with owners named after their run (`app-B`, `ask-F`). If the other run already set one up, use it. Never drop a shared resource such as `screen` to avoid sharing it with the other run; going without `screen` for UI tasks is a contract waiver the owner approves.
4. **Keep ports and folders apart,** and name the other run's in your briefs as not yours to stop or reuse.
5. **Its merges are normal movement of the integration branch.** Your tasks rebase onto them as onto any other merge. Never revert or rework the other run's merged work; tell it what you found instead.
6. **The user's settings are shared.** Both runs' test builds may write the same settings of the user's app. When `run-watch`'s `settings` line shows a change, find whose build made it, restore it, and tell that run, so it steers its task.
7. **Agree on the shared finish.** Steps that touch what both runs share (relaunching the user's app, the final comparison of their settings) are done once, by whichever run finishes last. If the other run hasn't answered all run (it may have died with its ledger still saying `running`), write to it once more at your finish; with no answer then either, do the shared steps yourself, stop nothing of its own, and say in your report that its ledger still looks active. Each run still runs the quick main check for its own report: the first to finish in a detached worktree, the last in the checkout ([finish.md](finish.md), step 4). The first to finish tells the other, and the last names both runs in its report.
8. **Forward findings.** Anything one run learns that affects the other (a flaky check, a new rule for the briefs, a shared file that broke) goes to the other run's thread at once.

## 3. When a window runs short or runs out

When a **5-hour** usage window runs out, the work that depends on it pauses on its own thread. Nothing moves to a small subscription, and your own thread never switches model or subscription. (A fast helper that hits its own limit switches to the next helper in section 4; weekly limits or budgets on a peer primary subscription may spill as below.) Waiting out short 5-hour resets beats a hand-off in two ways:
- the subscriptions stay used the way the user sized them;
- an agent that resumes on its own thread keeps everything it knew, which a successor would have to rebuild from notes.

### Before launching

If a wave won't fit in its primary subscription's 5-hour window, launch what fits and hold the rest until the reset, with a resume wake scheduled for just after it (below). Tasks routed to any other provider follow that provider's windows in the same way.

On a small plan such as ChatGPT Plus, each hour of a heavy task takes about a whole window (section 2). Launch such tasks one at a time, or together only when the contract accepts a near-certain pause, and schedule the resume wake as soon as they start.

### Watch the pace, not just the level

Compare each snapshot with the previous one. A window can go from comfortable to empty between two heartbeats, especially while a multi-agent task runs. Schedule the resume wake as soon as either is true for an active primary subscription:
- its 5-hour window is past about 85% (pass `--live` to `heartbeat` or run `provider-usage --only antigravity` while Antigravity runs, since `heartbeat` auto-flags 85% only for windows named `five_hour` unless marked in `watch.json` `"usage_marks"`);
- at its current pace, it will run out before your next heartbeat.

Do it early: once your own thread's window is empty, you can't act until it resets. Likewise, watch your own subscription's weekly window: if it passes about **95%** or will run out before the next heartbeat at its current pace (advancing or removing any lower crossed mark in `watch.json` `"usage_marks"` lets `heartbeat`'s built-in `>= 95%` check fire automatically), spill queued or running work to the peer primary subscription while you still can (clean handoff once per running task) or mark remaining tasks `parked`, write the ledger and final report on that wake, and finish cleanly rather than letting scheduled ticks fail for days after your own weekly window empties.

### The resume wake

The resume wake is a one-off wake-up a few minutes after the window's reset time (`resets_at` from `provider-usage`). The host reference shows how to schedule it.
- Record its ID and time in the ledger.
- Once work has stopped, set the ledger's status to `paused until <time>`.
- Remove the wake after it has fired.

Keep the heartbeat too. Its ticks while your own thread's window is empty simply fail, and the first tick after the reset resumes the run if the resume wake didn't.

### A running task hits its quota

Signs:
- its thread stops, goes idle or fails with a usage-limit or rate-limit error, without reporting back (an agent with no quota left can't send a report);
- `provider-usage` shows its provider's window at or near 100%.

Then:
0. **Check whether a weekly limit or weekly budget stopped it first:** if the stop came from a weekly window or run weekly budget (rather than a 5-hour reset), follow [A weekly limit](#a-weekly-limit) immediately instead of leaving the task paused for a 5-hour resume.
1. Leave it exactly as it is: its thread, worktree and uncommitted changes. Don't relaunch it, and don't hand it to another provider. The four exceptions: a task on a free model ([below](#a-task-on-a-free-model)), Claude work between the subscription and the owner's API credits as the contract allows ([Claude API credits](#claude-api-credits-use-what-would-expire)), a Fable task stopped by the Fable week, which continues on Opus 5.5 ([Fable 5.2](#when-the-fable-week-runs-out-or-passes-its-budget)), and a primary task stopped by a weekly limit or weekly budget when a peer primary subscription has ample room ([below](#a-weekly-limit)).
2. Make sure the resume wake is scheduled (scoped to that provider and window), and mark the task `paused` in the ledger with the blocking provider, window/bucket, and its expected resume time.
3. On the first wake after that window resets, check whether each task paused on that window is running again. If not, continue it on the same thread: "Your usage limit has reset. Continue the brief from where you stopped." This nudge doesn't count as the task's one nudge for silence.

### A task on a free model

A free model's limit isn't a window the run was sized on, and its reset can't be read or scheduled: OpenCode's free limit can stop both its free models together, for the whole computer, minutes into a run and again soon after a reset. So a task given to a free or Go model doesn't pause; it moves:

1. **It starts on Go, not the free tier.** A whole task given to this pool starts on `opencode-go/deepseek-v4.1-flash`, or on `opencode-go/glm-5.3-flash` while DeepSeek "requires Global regions": a stop in the middle of a task costs a handoff, and the free tier can stop at any moment.
2. **Between OpenCode's free tier, OpenCode Go and Antigravity's Gemini models, always.** They are the run's free and low-cost pool, so a task moves to the next one whenever a limit stops it, in any direction, without a line in the contract and without asking: to Go while either of its two models answers, to Gemini 4 Hydrogen at high while the Gemini windows have room (never to Neon or Orchestrator models, which stay outside the free pool), and to OpenCode's free models while they answer. OpenCode's free limit covers all its free models at once, so moving to the other free model doesn't get past it.
3. **Then to a paid model, also without asking.** When the whole pool is limited, move the task to Codex's GPT-6.1 Terra or Claude Sonnet at high, whichever has more room in its windows. You choose at the time; nothing about it goes to the user before or during the run.
4. **When the limit stops it** (its thread fails or stops on "Free usage limit reached", a quota error, or a rate-limit error that a retry a few minutes later still gets), delete its old thread's review-gate and helper wakes if listed and empty `<task>/helper-wake.txt` ([host-t3.md](host-t3.md#when-a-tasks-run-fails-or-is-cancelled)), save its uncommitted changes as a patch in the run directory, note in the ledger what it finished, and launch the next model at once on its own thread with the same brief, the same branch and worktree where the host allows (else a new one with the patch applied), and a handoff note: what is done, what is left, where the patch is.
5. **Don't wait for the limited model,** and don't move the task back when it recovers. If the next one is limited too, take the one after; only when the pool and both paid models are all limited does the task pause, or park at the end of the run.
6. **In the report,** say which model finished the task, and when and why it moved.

### Your own quota

You stay on your own provider and model for the whole run. Never switch your own thread to another provider or model to keep going. In T3, a self-switch ends your turn on the spot and leaves stale records behind (see [host-t3.md](host-t3.md#when-a-window-runs-out)).

Your turns are short, so they rarely run out halfway. When your window is nearly used up, schedule the resume wake, update the ledger and end your turn. After the reset, the resume wake (or the heartbeat) wakes you on the same subscription.

You don't need a stand-in orchestrator on another provider for this, not even a cheap model:
- the host's scheduler wakes you after the reset, with no model running in between;
- a stand-in would itself need a model switch on your thread, or a scheduled wake of its own;
- it would put a weaker model in charge of decisions about the run.

### A weekly limit

If a provider's weekly window runs out or passes its run weekly budget with work left (Claude's Fable week is different: its task continues on Opus 5.5 on the same thread, [Fable 5.2](#when-the-fable-week-runs-out-or-passes-its-budget)):

- **If a provider's weekly window ran out, resets within a few hours, AND the run's weekly budget still has room:** wait, as for a 5-hour window (and re-check the run's cumulative weekly budget before resuming after the reset — a reset never refills a spent run budget).
- **Peer primary spillover** (when one peer primary subscription — Claude Max 20x or Antigravity Ultra — runs out of its weekly window with reset many hours or days away, OR passes its run weekly budget even if the provider's window resets soon, while the other peer primary subscription named in the profile has **ample room** — its 5-hour window is under about **50%**, its weekly window is under about **65%**, and its active run weekly budget still has room for the moved task plus its remaining reviews and helpers — enabled by default between peer primary subscriptions unless disabled in the contract):
  - **Queued or not-yet-started tasks** in later waves may route to the peer primary subscription; update the receiving subscription's ledger budget/tracking and `watch.json` `"usage_marks"`, and record the move in the ledger and the final report.
  - **A running task** stopped by a weekly limit or weekly budget on one primary subscription may move **at most once per task** to the peer primary subscription via the clean handoff path:
    1. Delete the old thread's review-gate and helper wakes first (`list_scheduled_tasks` -> `delete_scheduled_task`) and empty `<task>/review*/wake.txt` and `<task>/helper-wake.txt`.
    2. Stop the predecessor and drain its delegates safely (**never call `t3_thread_interrupt` on a delegate**): on a run-budget stop, send the old thread a short stop message telling it to stop editing, `task_cancel` every running delegate it started, confirm each stopped via `task_status`, and stop (interrupting the top-level old thread if it does not stop promptly); on a quota stop, list active subagents (`t3_thread_list` `includeSubagents: true`), wait for running delegates with `t3_thread_wait`, and if a file-editing helper remains active and cannot be drained safely, mark the task `parked` instead of launching a second writer; settle finished child threads and stop/wait on leftover OS background jobs and leases ([integration.md](integration.md#cleanup-after-a-merge), steps 2 and 3).
    3. Cancel any queued messages on the old thread (`t3_queue` list -> cancel; [host-t3.md](host-t3.md#when-a-window-runs-out)), then re-read `t3_thread_read` right before snapshotting to confirm the old thread is `idle`, its queue is empty, and zero subagents remain active (if a completion woke it, interrupt the top-level thread and clear again).
    4. Save any uncommitted changes as a patch in `<run directory>`.
    5. Launch a new thread on the peer primary subscription in the same branch and worktree (`existing_worktree` in T3; or, where the host cannot reuse the worktree, base a new worktree on `<task branch>` with a handoff branch such as `<task branch>-handoff` and apply the saved patch) with a [continuation brief](task-brief.md#continuation-brief): rewrite harness-specific helper sections for the new provider/model, preserve completed `<task>/review*/` artifacts/rounds so unchanged rounds are not rerun, replace `<worktree path>` and `<task branch>` when using a fresh handoff worktree, and tell `review-gate` **both** authoring families when the handoff crossed between Claude and Gemini so cross-review covers both ([Reviews: the review gate](#reviews-the-review-gate)).
    6. Update `watch.json`: preserve predecessor dollar tracking under `"<task>-prev": {"thread": "<old>", "status": "stopped"}` (plus `"computer"` if elsewhere — noting `run-charts` does not merge `<task>-prev` onto `<task>`, so give `<task>` the combined helpers list from both threads in `facts.json` and note the predecessor's cost beside it), set `<task>`'s new `thread`, `harness`, `model`, `launched` (to the successor's launch time), and `worktree`/`branch` (if using a fresh handoff worktree), clear stale `session` / `session_log`, run `scripts/run-watch <run directory> --forget-session <task>` on the task's computer, settle the old thread, update the receiving subscription's ledger budget/tracking and `watch.json` `"usage_marks"`, and record the move (plus any leftover old worktree/branch for post-merge cleanup) in the ledger and report.
- **Small plans never absorb primary tasks:** never move a primary task to ChatGPT Plus, OpenCode Go or Copilot on quota, and never switch your own thread.
- **Otherwise** (the peer primary lacks ample room, spillover is disabled in the contract, or the task already moved once), mark remaining unstarted or stopped tasks on that provider `parked` (keeping uncommitted patches / `KEEP` for started work), finish the run, and report. Whether to wait for the reset or move further work is the user's decision.

### Always

Never work around a limit silently. The report says which tasks paused, for how long, and why.

### Claude API credits: use what would expire

The owner may have Claude API credits beside the Claude subscription: in T3, a second Claude instance (`claudeAgent_claude_api`) runs the same models, billed to the credits. The credits are dollars that expire, not windows that reset, so:

- **Read them in the usage snapshot.** `provider-usage` reports them under `claude_api`: the owner's grants in `api-credits.json` beside the provider profile (each grant's amount, expiry, and the balance the Console showed, with when), less the API spend T3 has logged since at list prices, soonest-expiring grant first. It is an estimate; say so, with the time of the Console reading. An estimate marked `incomplete`, or an error, counts as nothing left.
- **Choose each task's Claude instance at launch, in the contract.** While a grant expires within about a week with money left, Claude tasks and Claude reviewers run on the API instance first, sized to use what would otherwise expire and no more. Otherwise they run on the subscription. Your own thread stays on the instance it runs on.
- **The account is the safeguard against overspending.** Use the API instance only while the owner's API account has no payment method: running out then fails requests instead of billing, and the task moves on as below. If the account has one, the contract must name how much may be billed beyond the credits, or the API instance isn't used. Either way, keep a reserve: launch no new work on it once the estimate is below about $20 for each API task already running: costs reach the logs only as each result ends, so the estimate trails what running tasks spend.
- **Moves, each at most once per task:**
  - to the subscription, when the credits' estimate runs out (or the API instance reports the credits used up): the rest of that task continues on the subscription, on its own thread, as a free model's task moves on ([A task on a free model](#a-task-on-a-free-model));
  - to the API instance, only if the contract allows it (the owner uses the credits as a backup), when the task's Claude subscription window is used up and its reset is hours away, and only within the reserve. A task goes to the API instance at most once, so a task that came back to the subscription when the credits ran out pauses there for the reset.
- **In the contract,** give each grant's estimated balance and expiry, which tasks run on which Claude instance, and whether work may move to the API instance as a backup. In the report's usage line, give the credits' estimated balance at the start and the end, with what expired during the run apart from what was spent.

### Fast helpers: Antigravity and OpenCode

Two providers offer fast models that cost the run little. Handing them research and simple steps saves the task agent's context and its subscription for the work that needs judgment:

- **Antigravity:** `gemini-4-hydrogen-high`, Gemini 4 Hydrogen at high reasoning (in T3, `gemini-4-hydrogen` with the option `thought_level` `high`, as T3 lists every Antigravity model since 2026-11-20; `agy` keeps the level in the name), which replaced Gemini 3.8 Flash. While Antigravity still lists Gemini 3.8 Flash (`gemini-3.8-flash` in T3, `gemini-3.8-flash-high` for `agy`), it is the fallback for a Hydrogen that Antigravity reports unavailable; never Hydrogen through OpenCode, where `opencode/gemini-4-hydrogen` bills per request.
- **OpenCode:** only its two free models that are good enough: `opencode/deepseek-v4.1-flash-free` and `opencode/glm-5.3-flash-free`, each with `{"id": "variant", "value": "high"}`. When the free tier stops them: `opencode-go/beam-free`, free for a limited time and outside both the free tier's limit and the Go plan's, then the same two models on the owner's flat-rate OpenCode Go plan, `opencode-go/deepseek-v4.1-flash` and `opencode-go/glm-5.3-flash`, all with the same option. Its other free models, Go's Iceman among them, aren't good enough. Its `opencode/` paid models bill the owner per request (`opencode/deepseek-v4.1-flash`, without `-free`, is one). Go's other models count far more heavily against the plan. Use none of these.

These models stay fast at high reasoning, and the extra reasoning is what makes their results dependable. Fast helpers stay strictly on the listed fast models (never Gemini 4 Carbon or Argon, Hydrogen at extra high, GPT-OSS 120B, OpenCode's paid models, or Go's larger models). Advanced sub-tasks stay on plain Gemini 4 Neon as below, while Antigravity primary tasks and Antigravity Claude reviews/tasks follow sections 1, 2 and `Reviews`.

**What they take,** as often as it genuinely helps, with no fixed count:
- **Research and retrieval:** web and documentation research, searching a codebase, logs or many files, surveying how other projects solve a problem, collecting facts, API details or evidence, comparing options against named criteria, condensing long material.
- **Simple, fully specified steps:** a mechanical edit across many files from an exact rule, renames, reformatting, boilerplate from a given template, extracting facts from named files, a quick lookup.

**How a task uses them,** in T3 through `delegate_task` (section 5):
- **as a sub-task** (`mode: "wait"`, `timeoutMs` at most 45000), only for a step of seconds the task needs before it goes on. The wait returns after at most about 45 seconds, and a wait that times out doesn't stop the helper: its completion still wakes the agent. Anything longer runs in `mode: "async"`: a research lane as below, or a step with `role: "general"`;
- **as a research subagent** (`mode: "async"`, `role: "research"`), for a longer lane that runs while the task's agent does other work, such as surveying prior art while it reads the code. Its completion wakes the agent. A task may run several lanes at once when their questions are independent.

You may use them too, for the run's own chores: collecting thread times for the report's charts, condensing handoffs, research while planning.

**What they never take:** a whole task, a design decision, a bug with an unknown cause, code changes that need judgment, the merge gate, or the orchestration, not even as a stand-in while a 5-hour window resets (section 3). They are task agents only when the user asks for it ([A task on a free model](#a-task-on-a-free-model)). OpenCode's two flash models, Hydrogen (Light on non-Gemini changes), and plain Gemini 4 Neon at extra high review only where the `review-gate` skill's levels put them ([Reviews](#reviews-the-review-gate)); no other Gemini model reviews (neither `Orchestrator (Neon)` nor plain Neon at `high`).

**Every result is checked** by the agent that asked, before it relies on it. For research, the helper gives a source for each claim (a link, or a file and line), and the agent checks the claims it builds on. For a step, a diff, a test or a quick read.

**They run with the owner's own setup.** A helper loads the owner's configuration for its harness, including their MCP servers, through which it can reach the owner's running app. So every helper's prompt says: stay read-only, apart from the files a step names; run no tests, scripts or command that may ask for approval, since nobody is there to give it; never commit, merge, or touch the integration checkout; don't use tools that reach the owner's apps or services (speaking, messaging, their app's own tools); never ask the user anything. A helper that waits on an approval anyway is stopped and launched again once, as the "Help available" text says.

**Limits: switch, don't wait.** The usage of OpenCode's free tier can't be read, so watch its helpers themselves. Antigravity's and OpenCode Go's can, so check them as well as watching their helpers.
- **Antigravity Hydrogen comes first** while `gemini_models_five_hour` is under about 85% and the Gemini weekly budget has room: every Gemini model draws on the Gemini group's one 5-hour and one weekly window, and the owner uses them in Antigravity too (Hydrogen draws far less per call than Neon on the same Gemini windows). Before each wave, and on each wake while tasks run with Hydrogen helpers, read `antigravity` in the usage snapshot (live via `heartbeat --live` or `provider-usage --only antigravity` when near 85% or the weekly mark): while `gemini_models_five_hour` is at or past about 85% or the Gemini weekly budget is used, omit Hydrogen from new briefs and steer running tasks with Hydrogen fast helpers (`"Gemini helpers are out <for this run (Gemini weekly budget spent) | until the Gemini 5-hour reset>: skip Hydrogen and start fast helpers on OpenCode."`) so OpenCode leads until the 5-hour reset (or for the rest of the run once the Gemini weekly budget is used). A helper that hits the limit anyway says so with a quota or rate-limit error.
- **OpenCode's free models are rate-limited, model by model.** Under load, most requests come back `429` and OpenCode quietly retries them, so a helper slows down rather than fails. The signs:
  - a step takes several times longer than the same kind of step did earlier;
  - `task_status` stays `working` while its child thread shows nothing new for several minutes;
  - it ends with a rate-limit (`429`) or "Upstream request failed" error.

  OpenCode's log (`~/.local/share/opencode/log/opencode.log`) records only that last error, not the retries before it. The owner's OpenCode console lists every request.
- **OpenCode Go has limits of its own:** per 5 hours, per week and per month. The console shows one set of meters for all models, and the owner's own use counts too, so plan as if every Go model shares one limit. Before each wave, read `opencode_go` in the snapshot: while `five_hour`, `weekly` or `monthly` is past about 85%, leave Go's DeepSeek and GLM out of new briefs, and start a whole free-pool task on Gemini 4 Hydrogen instead of Go. When it runs out, Go's requests fail with a quota error. A quota error from one Go model still means trying the other: if the limit is shared, that fails at once. Extra Usage stays off, so it can't bill past the plan: never turn it on. A Go model that "requires Global regions" isn't limited, just unavailable: use the other one. Beam Free's offer can end at any time: when it stops answering, move on.
- **When a helper is limited,** cancel it (`task_cancel`) and switch. A returned wait says nothing about a helper, since a wait that times out doesn't stop it: judge how long it has run from its thread's `createdAt`, and whether it is stuck from its last activity (`t3_thread_read` with `view: "activity"`, or `createdAt` before any): nothing new for several minutes is the sign to look at `task_status`. Then follow the order from your brief's first target:
  1. **Hydrogen first (default when Gemini has room):** if Hydrogen is limited, move to OpenCode's free tier (`deepseek-v4.1-flash-free`, then `glm-5.3-flash-free`).
  2. **OpenCode's free tier:** on OpenCode's free tier, delegate the same prompt again to its other good free model, unless the error was "Free usage limit reached", which covers both.
  3. **Go:** then delegate it to `opencode-go/beam-free`, then to `opencode-go/deepseek-v4.1-flash`, then to `opencode-go/glm-5.3-flash`, as far as you need.
  4. **Antigravity fallback (if OpenCode started first):** if OpenCode started first because Antigravity was busy earlier and `gemini_models_five_hour` now has room, try Hydrogen before Copilot.
  5. **Backup:** when Antigravity and OpenCode are limited, delegate it to Copilot (see "Backup helper" below), if its budget has room.
  6. **Yourself:** when every helper is limited, do the work yourself.

  Try a limited OpenCode model again only on a later step, and drop it for the rest of the task if it is still slow. After an Antigravity quota error, leave that model group alone until its window resets (`resets_at` in the snapshot). Neon and Hydrogen share the Gemini group's windows, so one running out stops the other too.
- **Switching moves helper work only.** Helpers are free or small, not the primary subscriptions the user sized for the run, so their work moves freely between helpers. Primary tasks pause on 5-hour resets and spill between peer primaries only on weekly limits or weekly budgets (section 3).
- **Record it.** The ledger gets each task's helper use (provider, model and level, and for what, with counts) and every limit and switch. Where the limits began goes into the profile's calibration.

### Advanced helpers: Gemini 4 Neon

Some sub-tasks need more judgment than the fast helpers give, but are still bounded and checkable:
- **Deep research and synthesis:** comparing designs or libraries against the task's criteria, explaining how an unfamiliar part of the code works, condensing a long specification into the decisions it forces.

### Computer use needs the screen

Computer use works only while the Mac is awake and unlocked, and on windows the agent can capture. In the first overnight run, every real-screen check failed: the screen had locked itself, and Stage Manager, which can hide windows from Codex's screen capture, was on. So, whenever a task or helper step will operate the real screen:

1. **Settle it in the contract.** [machine.md](machine.md#2-build-the-permissions-list) reads the settings and lists what to change: automatic screen lock off, Stage Manager off, and the permissions computer use needs. You keep the display awake with `caffeinate -i -d` for the whole run ([machine.md](machine.md#4-keeping-the-computer-awake)).
2. **Check again before the step runs.** The screen is locked when this prints `<true/>`:

   ```sh
   ioreg -n Root -d1 -a | grep -A1 CGSSessionScreenIsLocked
   ```

   If it is locked, or the app's window can't be captured, don't retry. For a task with `Live UI check: required` (not waived in the contract), the task does **not** merge: it reports `ready` with `"live UI check pending"` and the exact scene, and the report lists it under "Not finished" for the owner. Advisory real-screen checks on non-required or waived tasks go under "Couldn't check" and merge on their other checks (unless that check is the task's main deliverable).

This needs T3, which can launch child tasks on other providers. In T3, when a task has work suited to another provider and that provider has room, add a "Help available" section to the brief. For Codex:


For the fast helpers, add this section, with examples from the task:
