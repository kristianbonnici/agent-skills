# Tasks on another computer

In T3 Code, the owner's computers can be linked to one another (Settings → Labs → Linked environments), and every T3 tool then acts on a linked computer when given its `environmentId`. A run can place a task there: to keep the computer the owner uses every day free, to spare a weak computer the heavy work, or for a tool that exists on one computer only. Plain Claude Code and Codex hosts can't reach another computer: under them, every task runs where you run.

"Your computer" below is the one you, the orchestrator, run on; "the other computer" is any linked one. Name each computer by its `LocalHostName` (`scutil --get LocalHostName` on macOS, `hostname -s` elsewhere), the name of its section in the owner's profile ([routing.md](routing.md#6-the-owners-profile)). The examples use two made-up Macs: `studio-mac`, the daily one, and `den-mac`, an older one that is always on.

## 1. When a task goes elsewhere

Tasks run on your computer unless the contract places one elsewhere and says why. Three reasons count:

- **Capacity:** the owner works on the daily computer during the run, or a weak computer should get only light tasks.
- **A tool that exists only there:** a harness or helper installed and signed in on one computer, a simulator, a device, a signed-in service.
- **The owner's wish.**

Read what each computer can do from its `## Machine` section in the profile before placing anything: its role, what is installed and signed in there, and what can't run there. A preference that names a tool ("computer use on Codex") applies only on a computer where that tool exists.

- **Keep a task that uses the real screen** on a computer whose warm-up you ran with the owner at it. The warm-up needs them at that computer's keyboard ([machine.md](machine.md#3-the-warm-up)), so a screen task on a computer they won't sit at before they leave stays off it.
- **A weak computer** (an older chip, little memory or free disk, on battery) takes fewer tasks at once, and no task whose builds or installs are heavy there: on an Intel Mac, for example, some package installs compile from source and take far longer.
- **A computer that doesn't answer now** (`t3_environment_links` shows its `status`), or whose link expires before the run's estimate plus a day (`expiresAt`), gets no task. Ask the owner to link it again before they leave, or place its tasks on your computer.

## 2. Discover each computer

Before the contract, for your computer and each linked one:

1. **Who you are:** `t3_environment_read` with no `environmentId` gives your own `environmentId`, label and platform. Every brief elsewhere needs your `environmentId` to report back to you.
2. **What is linked:** `t3_environment_links` lists each linked computer's `environmentId`, label, `status`, `access` and `expiresAt`; `t3_environment_read({environmentId})` gives its platform (`os`, `arch`). Use only a computer with `access: "full-access"`, since tasks commit and run commands there.
3. **Its providers and models:** `orchestrator_capabilities({environmentId})`. Read the targets for a computer from its own catalog, and never copy one computer's into a brief for the other: model IDs and their options differ by computer (one may list a model with its reasoning in the ID, the other the same model with a reasoning option), and a provider instance or helper may exist on one only. The same holds for the "Help available" sections of a brief elsewhere: list that computer's targets.
4. **Its projects:** `t3_project_list({environmentId})` and the entry whose `workspaceRoot` is the repository's checkout there. A repository checked out there that isn't a T3 project yet needs `t3_project_create({environmentId, workspaceRoot})`. A repository not checked out there at all is a pre-flight item: clone it only if the contract says so.

5. **How you reach it outside its tasks:** when its profile section names an SSH alias (`SSH: <alias>`) and `ssh -o BatchMode=yes -o ConnectTimeout=15 <alias> true` passes, over SSH; otherwise through one machine thread of this run (section 10).

Record each computer in the ledger: its name, `environmentId`, label, platform, role, project IDs, the targets you read, and how you reach it.

## 3. Pre-flight on the other computer

Run the commands below on the other computer before you post the contract, so their findings go in it: over SSH yourself when its alias works, else through the run's machine thread there (section 10), which runs in the project's own checkout and changes nothing there but fetched refs, and puts their output in its reply, which you read with `t3_thread_read({environmentId, threadId})`. Never through a thread of the owner's.

- **Power and disk:** `pmset -g batt` (on battery is a pre-flight item: ask the owner to plug it in before they leave) and free disk (`df -h /System/Volumes/Data`).
- **Active runs there:** ledgers under `${XDG_STATE_HOME:-~/.local/state}/agent-skills/long-horizon-orchestrator/` whose status line says `running` or `paused`. Another run there shares that computer's capacity and its leases ([routing.md](routing.md#running-beside-another-orchestrator)).
- **Its repositories against the remote:** for each repository the run touches, `git fetch origin`, the branch it is on, whether it is clean, and how its local integration branch and the remote's differ (`git rev-list --left-right --count origin/<integration branch>...<integration branch>`: the remote's commits it lacks, then its own the remote lacks).
- **Its installed skill versions:** `metadata.version` of this skill and of `review-gate` in the copies its harnesses read. Tasks there follow the review gate from their own worktree's copy, so a difference matters only for the scripts the brief names there and for `run-watch`, which you run there on every wake over SSH (section 8): name the paths that exist on that computer, from that computer's skill folder. A copy there older than 5.10.0 can't be run that way: copy `run-watch` from a newer one into the run directory there, as the last paragraph of this section says, and give its path as `"run_watch"` in that computer's `"machines"` entry in `watch.json`.
- **The run file, first, before anything else is written there:** `<skill folder there>/scripts/prune-runs --mark-running <run directory> --orchestrator <your LocalHostName>`, which writes `<run directory>/run.json` there, `{"run": "<run ID>", "role": "other computer", "orchestrator": "<your LocalHostName>", "started": "<time>"}`, whole each time and under the run's lock, so a new round's pre-flight drops the earlier finish's time before any task there starts, and never while a prune of older runs is removing files there (it waits for that prune to end, so give the shell call an 11-minute timeout, 660000 ms; exit 75 after ten minutes, or a call that timed out: run it again). Record the `started` time it prints in the ledger: the finish gives it back. It takes only an empty folder or one already holding its `run.json`; a run folder there from a pre-flight that wrote none takes `--adopt`. Copies of this skill before 5.9.2 never prune a run folder without its ledger, and 5.9.2 went out only together with 5.10.3, so every copy that can prune one takes the lock. A `--mark-finished` refused with another `started` time after a timed-out `--mark-running` was run again means the first call wrote last: give it the time the refusal names, when no new round began there since. With no ledger on that computer, it is what makes the run directory a run's for `prune-runs` there ([machine.md](machine.md#6-shared-resources-and-disk)), so the cleanup gate's `--scratch` and `--harness-temp` and the `--size` line work there too. A copy of this skill there older than 5.10.3 lacks `--mark-running` and the lock: copy `prune-runs` from a newer one, as the last paragraph of this section says.
- **Leftover processes and a start snapshot:** `ps -axo pid,lstart,command`, saved in the run directory there, so the finish can tell the run's leftovers from the owner's own.

The commands here are macOS's; on another system (the `os` from section 2), use its own, as [machine.md](machine.md) says.

Once the owner has approved the contract, start that computer's keep-awake, over SSH or through the machine thread (section 10): `nohup caffeinate -i -t <seconds> >/dev/null 2>&1 & echo $!`, with `-d` too if a task there uses the real screen ([machine.md](machine.md#4-keeping-the-computer-awake)). Record its process ID in the ledger and in `<run directory>/keep-awake.pid` there. On battery, `caffeinate` doesn't stop a sleep that a closed lid or a flat battery brings.

The same way, start that computer's usage sampler for the whole run, for its own processor, graphics, memory and free disk: `mkdir -p <run directory>/usage && nohup <skill folder there>/scripts/usage-sampler --machine-only <run directory>/usage >/dev/null 2>&1 & echo $!`, then `ps -p <pid>`. `--machine-only` reads no subscription: the subscriptions are shared, and your computer's sampler reads them for the whole run. Record its process ID in the ledger and in `<run directory>/usage/sampler.pid` there. Its samples stay in that folder there until the finish brings them over (section 9). A copy of this skill there older than 5.8.0 has no `--machine-only`, `run-costs --task` or `share-usage`: they stand alone, so copy the three scripts from a newer copy of this skill (`git show <commit>:skills/long-horizon-orchestrator/scripts/<name>` into the run directory there), or start that sampler without the flag (it then reads the subscriptions as well, which nothing uses) and let the report name what didn't arrive.

## 4. In the contract

Add one part, **Computers**, when any task runs elsewhere:

- each computer: its role, why it gets the tasks it gets, and its limit on tasks at once and on heavy builds at once (the `cpu` lease's slots there): leases and limits are per computer, while subscriptions, live usage and the run's budgets are shared by all of them;
- what its pre-flight found that needs the owner before they leave: power, free disk, another active run, unpushed commits, a link that expires, a repository missing there;
- the run branch (or, under "leave on branch", the task branches) and the briefs branch below, which are pushes the owner approves with the contract;
- what you won't be able to watch there (section 8).

Each task's line gives its computer, and its reason when it isn't yours.

## 5. Briefs and rules reach it through git

The computers share no files. The run directory lives on your computer; a task elsewhere keeps its files at the same path under its own home folder (`${XDG_STATE_HOME:-~/.local/state}/agent-skills/long-horizon-orchestrator/<run>/<task ID>/`), and its final message carries its whole handoff, since you can't read that folder.

The common file and the briefs reach it on a throwaway branch of the owner's private state repository, `lho/<run>-briefs`, which holds only `common.md` and `<task ID>.md`, and, from the finish, a `computers/<LocalHostName>/` folder for each other computer with its machine samples and costs (section 9), which only `scripts/share-usage` writes:

- Make it from a worktree of that repository in your run directory (`git worktree add --detach`, then `git switch --orphan lho/<run>-briefs`), commit the files, and push the branch. Never commit anything else there: it is the one exception to the profile's rule of committing nothing else in that repository ([routing.md](routing.md#6-the-owners-profile)). Remove that worktree at the finish.
- The launch message is short: it says to run, in one shell call, `git -C <state repository there> fetch -q origin lho/<run>-briefs`, then `git -C <state repository there> show FETCH_HEAD:common.md` and `git -C <state repository there> show FETCH_HEAD:<task ID>.md` (every command in that repository, since `FETCH_HEAD` is its own), with `GIT_TERMINAL_PROMPT=0` and `GIT_SSH_COMMAND='ssh -o BatchMode=yes'` so nothing can prompt, to read both in full and do the brief, and to fetch the common file again before its merge gate. If the fetch fails three times a minute apart, the task does nothing else and ends with a report whose first line is `[long-horizon-orchestrator] run=<run> task=<task ID> status=failed`, so the launch message carries the run and task IDs and the brief's whole report-back call (section 7), which the task makes then too.
- In the brief and the common file, the line that points to the common file names that `git show` instead of `<run directory>/briefs/common.md`, which doesn't exist there.
- A rule added during the run is a new commit and push to that branch, and, for a running task, a steer as well (`t3_thread_send` with its `environmentId`, mode `steer`), as for any task ([task-brief.md](task-brief.md#one-common-file-for-every-brief)).

## 6. Commits travel through the remote

Your computer's checkout may be far behind or ahead of the other's, and a branch on one computer doesn't exist on the other. So a run with a task elsewhere integrates on a **run branch** on the shared remote, `lho/<run>`, in each repository it changes. It stands in for the contract's integration branch (the branch checked out where the run starts, `main`, `dev`, …), which below is "the integration branch" on each computer:

1. **Start it from the newest copy of the integration branch.** Compare each computer's local integration branch with the remote's (the pre-flight's counts). The computer whose copy holds all the others' commits pushes it as `lho/<run>`; when it is the other computer, its pre-flight pushes it, over SSH or through the machine thread (section 10). If two computers each hold commits the other lacks, that is a pre-flight item for the owner: don't pick one for them.
2. **Every task, on any computer, bases on it and merges into it with a plain push,** the tasks on your computer too, so every brief of the run gets this merge gate in place of the fast-forward, and the common file's rule on pushing names this push as the one allowed ([task-brief.md](task-brief.md#a-run-with-a-task-on-another-computer)). Launch with `workspaceStrategy: {type: "worktree", baseRef: "origin/lho/<run>", branch: "<task branch>", startFromOrigin: true}`. Its merge gate is: `git fetch origin`, `git rebase origin/lho/<run>`, the full validation, then `git push <remote> HEAD:refs/heads/lho/<run>`, never forced. A rejected push means the branch moved: fetch, rebase, validate and push again. When a task changes two repositories, it pushes the private one first. The default merge policy, where a task fast-forwards the integration checkout itself, works only for tasks on your computer, so the whole run uses the run branch instead. Under "leave on branch", the run branch is pushed only as the tasks' shared base, and no task pushes to it: each pushes its reviewed, rebased task branch instead, once, never forced (a later change goes up as `<task branch>-r<n>`, [task-brief.md](task-brief.md#a-run-with-a-task-on-another-computer)), a dependent bases on its predecessor's pushed branch (`baseRef: "origin/<predecessor branch>"`, `startFromOrigin: true`), and the contract names those branches as the pushes it approves.
3. **Verify merges in your own worktree of the run branch,** kept in the run directory (`git -C <checkout> worktree add <run directory>/integration lho/<run>`, on a local branch `lho/<run>` made from `origin/lho/<run>` if your computer didn't push it), not in the owner's checkout, which stays as it was until the finish; when the repository is the skills' own, your installed skills then don't change under you. On a wake that brings a report, `git fetch origin`, fast-forward that worktree, and check `git merge-base --is-ancestor <task head> origin/lho/<run>` ([integration.md](integration.md#verifying-a-merged-report)). Give that worktree as `repo` in `watch.json`, and `lho/<run>` as its `integration_branch` (under "leave on branch", leave both as Prepare sets them).
4. **At the finish,** read "the integration branch" and "the integration checkout" in [finish.md](finish.md)'s steps 2 to 9 as `lho/<run>` and your worktree of it: the end-state check, the final check's detached worktree, and the `--repo` of `run-charts` and `report-offer`; and "nothing was pushed" as "nothing was pushed but the branches the contract names". In finish.md's step 5, before the report is written, so it can say how they went, fast-forward each computer's local integration branch to the run branch where its checkout is on that branch, clean, and behind it (your computer yourself; the other in its finish steps, over SSH or through the machine thread); under "leave on branch", leave them as they are. A branch that can't fast-forward stays as it is, and the report says so. Remove your run-branch worktree (`git worktree remove`; it holds no work) only in step 10, once the report's scripts have used it. Pushing the integration branch, and deleting the branches the run pushed, stay the owner's: the report names each branch the run left on the remote.
5. **The profile and the lessons follow the state repository's run branch.** When the state repository's run branch holds commits its `main` on the remote lacks (the run changed that repository, or another computer held unpushed commits there: the pre-flight's counts, the state repository's among them; the contract then gives it a run branch too, started as in step 1), its `main` is not yours to push, and the owner's checkout of it stays as it is, its upstream included. Before the finish writes anything there (finish.md's step 5 at the latest), make a throwaway clone on the run branch: `git clone -q --branch lho/<run> "$(git -C <state checkout> remote get-url origin)" <run directory>/state-finish` (a clone, not a worktree: `lessons` needs a `.git` folder), whose `lho/<run>` tracks `origin/lho/<run>`. Run every `lessons` command of the finish with `AGENT_SKILLS_STATE=<run directory>/state-finish`, so it pulls from and sends to the run branch, never `main`. Once the profile's calibration is updated, carry its uncommitted changes over as a patch, not a copy, so changes the run branch already holds stay: `git -C <state checkout> diff -- "$(realpath <profile>)" > <run directory>/profile.patch` (the file the link points to, never the link), then `git -C <run directory>/state-finish apply --3way <run directory>/profile.patch` (if it doesn't apply cleanly, stop: keep the patch and the clone, commit nothing of the profile, and say so in the report). Commit only that file, and `git push`, never forced (if it is rejected, `git pull --rebase` and push again; if that rebase stops on a conflict, `git rebase --abort`, keep the clone, and say so in the report). After the push, in each computer's state checkout, `git fetch origin`, confirm `origin/lho/<run>` holds the pushed commit (`git merge-base --is-ancestor <pushed commit> origin/lho/<run>`), and fast-forward its `main` to it where it is on `main`, clean but for the profile, and an ancestor of `origin/lho/<run>`: yours yourself, the other computer's over SSH or through the machine thread, as in section 10 (its finish steps ran before the push). The profile edit left uncommitted there since the warm-up blocks the fast-forward, so first restore it with `git checkout -- "$(realpath <profile>)"`, only when `cmp` shows it matches the fetched copy (`git show origin/lho/<run>:<its path>`) byte for byte; one that differs, or a checkout that can't fast-forward, stays as it is, and the report says so. List the state repository's `main` with the integration branches the owner pushes, and remove the clone in finish.md's step 10 only once `git -C <run directory>/state-finish status -sb --untracked-files=all` prints `## lho/<run>...origin/lho/<run>` alone, with no `ahead` (nothing unpushed, uncommitted, untracked or mid-rebase) (`rm -rf` with its literal path, in a call of its own); otherwise keep it, with `KEEP` beside it, and name it in the report.

## 7. Launch and report-back

- **Launch** with `t3_thread_launch` as [host-t3.md](host-t3.md#launch-a-task) says, adding `environmentId` and that computer's `projectId`, and `modelSelection` from that computer's catalog. Record the task's computer in the ledger and in `watch.json` (section 8 says how).
- **Report-back:** the brief's `t3_thread_send` carries your `environmentId` as well as your `threadId`, so the message crosses to your computer. The brief also tells the task to end with the report as its final message, whether the send worked or not: when the send can't reach you (your computer asleep, the link down), you still read the report with `t3_thread_read({environmentId, threadId})`. A failed send is retried a minute apart, three times at most.
- **Every other call about it** takes its `environmentId` too: `t3_thread_read`, `t3_thread_wait`, `t3_thread_list` (for its `createdAt`, and its reviewers' and helpers' threads, which are on that computer as well), `t3_thread_configure`, `t3_thread_send`, `t3_thread_interrupt`, `t3_queue` and `t3_thread_organize`. At the finish, list each computer's unsettled threads in its own call.
- **What [integration.md](integration.md) does in a task's worktree** runs on that computer for a task elsewhere, over SSH or through its machine thread (section 10): doing the gate yourself, saving a stopped task's patch (into the run directory there; the report gives its path there). A fix-up, continuation or relaunch launches there, with its brief on the briefs branch. After a merge, settle its thread on the wake that verifies it, and leave the rest of its cleanup to that computer's finish steps.

## 8. Watching it

Give each task elsewhere `"computer": "<its computer>"` in `watch.json`, and set the top-level `"computer"` to yours, both by `LocalHostName`, never by T3's label; leave the key off every task on your computer. A task whose `computer` doesn't match yours is never read here (its worktree path would be another folder here). How it is watched depends on how you reach its computer (section 10):

- **Over SSH,** `scripts/run-watch` and `scripts/heartbeat` watch that computer as closely as yours. When its entry in `watch.json`'s `"machines"` says `"reach": "ssh <alias>"`, each `run-watch` (the heartbeat's too) makes one `ssh` call to it, in batch mode, through its login shell, with a time limit, and runs that computer's own copy of `run-watch` there, with `--as <computer>` and a `watch.json` for its tasks on standard input: every check of [run-watch.md](run-watch.md) runs there on its own processes, files and session logs (`hang`, `idle`, `approval`, `quiet`, `blind`, `hog`, `commit`, `report`, `disk`, `swap`, `dialog`, `keep-awake`, `sampler`, `vm`, `slept`), with the keep-awake's and the sampler's process IDs read from the files section 3 names there, and `leftover` for processes a stopped task left. Each of its lines names that computer, a one-time line (a hog, a blind task, a first VM or leftover line, a sleep, a commit or report, a disk fall) comes again until a result carrying it has arrived, its times go into your `times.log`, and the heartbeat's line gives that computer's free disk, swap, load, keep-awake and sampler beside yours (`unknown` for one it couldn't read there: check it by hand over SSH when it lasts; `<computer> not checked this wake` when the heartbeat's own `run-watch` failed: run it yourself), and says "nothing to act on" only when neither computer needs anything. The check writes nothing there but its own state file and `times.log` in the run directory there, and never changes the processes it reads. Read a task there as you read one of yours (SKILL.md, step 2 of "On every wake"): its thread when a line names it, it reported, or it is `blind`. A computer the check doesn't reach gives one `unreachable` line, and its running tasks are `blind` that wake, so you read their threads as below. The entry's optional keys, when that computer isn't laid out as yours: `"run_watch"` (the path of `run-watch` there; by default the first installed copy under `~/.claude/skills`, `~/.agents/skills` or `~/.codex/skills`), `"run_dir"` (the run directory there; by default this one's path under that computer's home folder) and `"shell"` (by default `"zsh -l"`); a relative path is taken from that computer's home folder.
- **Without SSH,** or while its computer is `unreachable`, `run-watch` reads nothing of a task there and calls it `blind` once, saying where it runs, and the heartbeat names it on every wake, so a wake with a task elsewhere is never idle. On every wake, read each such task with `t3_thread_read({environmentId, threadId})`: its status, its last message, and `pendingRequestCount`. A running task with a pending request is waiting for approval: interrupt its turn and tell it how to finish without that command. A failed or interrupted thread is nudged as on your computer ([host-t3.md](host-t3.md#when-a-tasks-run-fails-or-is-cancelled)).
- **Not watched there without SSH:** password dialogs, free disk and swap, sleep, the keep-awake, its usage sampler, and leftover processes. Its sampler records that computer's load all run, but you see it only at the finish, when its samples come over (section 9). Each brief elsewhere therefore asks the task to name in its report any dialog it saw, and to check free disk before a heavy build. When a task elsewhere has shown no progress for an hour, or reports a dialog or a full disk, send the machine thread the check: the keep-awake's and the sampler's process IDs, free disk, the system's password dialog ([machine.md](machine.md#7-during-the-run) gives the command), and processes naming the run directory or a task's worktree.
- **No `merged` line comes** for any task of such a run, on either computer: tasks push, and your worktree only fast-forwards from `origin/lho/<run>`, so the reflog `run-watch` reads names no task branch. Take each merge's time from the task's report-back, and confirm the merge with `git fetch` and `merge-base --is-ancestor`.

Without SSH, `run-watch` and `heartbeat` read only your computer, and the machine thread is what you see of the other one.

## 9. The ledger, the finish and the report

- **Ledger:** a "Computers" part beside "The computer": for each, its name, `environmentId`, label, platform, role, limit, how you reach it (SSH alias or machine thread), keep-awake and sampler process IDs, pre-flight findings and threads, and at the finish what was stopped and restored and whether its samples and costs arrived. Each task's row gives its `computer`.
- **Finish:** for each other computer, after your own finish steps 1 to 3, these steps run there: over SSH, yourself (section 10, where `share-usage fetch --ssh` takes the place of step 3), else through its machine thread. First its samples and costs come over, in this order, giving the paths that exist there:
  1. `<skill folder>/scripts/usage-sampler --final --machine-only <run directory>/usage`, the last machine sample, then `kill <the sampler's recorded process ID>`.
  2. `<skill folder>/scripts/run-costs <run directory> --from <watch.json's started> --task <ID>=<thread ID> --computer <its LocalHostName> --json <run directory>/costs.json`, with one `--task` for each task that ran there (the thread IDs your `watch.json` holds, which are that computer's own): what those tasks, their reviewers and their helpers cost, read from that computer's T3 records. There is no `watch.json` there, which `--task` stands in for.
  3. `<skill folder>/scripts/share-usage send <run directory> --state <state repository there>`: commits `usage/machine.jsonl` and `costs.json` as `computers/<LocalHostName>/` on the briefs branch and pushes it, never forced (a rejected push is made again on the branch's new head), with no prompt possible. It says what it sent. The folder on the branch is always this send's snapshot: a file it didn't find is taken off the branch, so a send that finds neither file exits 1 and leaves that computer with nothing there. Run it before the cleanup below, never again after the run directory's files are gone; a send that failed is run again once the files are back, never skipped.

  Then it stops the keep-awake by its recorded process ID, stops the run's leftover processes there against the pre-flight's snapshot, writes `run.json` there as section 3 says, with `--adopt`, if its pre-flight didn't (a copy of this skill older than 5.10.3, whose `prune-runs` is replaced by a newer one's first, as section 3 says, for every `prune-runs` step below), does the cleanup gate for the merged tasks of that computer ([integration.md](integration.md#cleanup-after-a-merge), with that computer's `prune-runs`), puts `KEEP` in the folders of unfinished tasks, fast-forwards the integration branches (section 6, step 4; under "leave on branch", not), runs `<skill folder>/scripts/prune-runs --mark-finished <run directory> --started <the time the round's --mark-running printed>` last (it refuses a later round's `run.json`, and writes the finish time into `run.json`, without which a later prune of older runs there never shrinks this run's folder; it waits up to ten minutes for a prune holding the run's lock, so give the call an 11-minute timeout, and exits 75 if it is still held: run it again, as after a timeout, since the finish there isn't done until it exits 0), and reports free disk, the run directory's size there, what `share-usage` sent and what it couldn't do. Settle the threads there with their `environmentId`, the machine thread last.
- **Bringing them in:** once those finish steps are done, and before the charts (finish.md step 8), run `<skill folder>/scripts/share-usage fetch <run directory> --state <state repository> --expect <each other computer, comma-separated>`, with `--ssh <name>=<alias>` for each computer reached over SSH (its files then come straight from there). It writes each computer's files into `<run directory>/computers/<LocalHostName>/` (`usage/machine.jsonl` and `costs.json`) and names any computer that sent nothing. `run-costs` adds every `computers/<name>/costs.json` by itself, and the facts' `"usage": {"folder", "computers": [...]}` lists every computer, yours first, each with its name and role from the ledger ([final-report.md](final-report.md#the-runs-facts)), so the run map draws each one's machine charts with a picker. Record in the ledger what arrived.
- **Report:** when tasks ran on more than one computer, each task names its computer; "Side effects" and the cleanup are given per computer; one line says what wasn't watched on the other computer; and "What needs you" lists the branches left on the remote and any integration branch that couldn't fast-forward.
- **What stays on the other computer:** a task's pictures there can't reach the report or the run map, which read files on your computer. The report lists them with their paths on that computer, under the task, and the run map shows none for it.
- **What comes over:** each computer's machine samples and costs, as above. The costs count every task, its reviewers and its helpers, and say which computer each ran on (the report's cost paragraph gives the total per computer); the usage line gives each computer's peaks and free-disk change, and the run map's usage panel shows one computer's machine charts at a time, chosen with its picker. A computer whose files never arrived is named in both: its tasks are "not counted" in the costs, and the usage line says no samples arrived from it, while the charts draw the others.

## 10. Reaching it: SSH first, one machine thread second

Two ways reach the other computer outside its tasks. Task threads always launch, report and get read through the T3 link (section 7); what follows is for everything else, the run's shell chores there.

**SSH, when the profile names an alias.** The owner may set up SSH between their computers (ordinary OpenSSH over Tailscale, so it works away from the home network too), with an alias per computer in `~/.ssh/config` and verified host keys, and name it in that computer's profile section: `- SSH: den-mac (SSH over Tailscale, set up by the owner, <date>)` ([routing.md](routing.md#6-the-owners-profile)). At discovery (section 2), check it: `ssh -o BatchMode=yes -o ConnectTimeout=15 <alias> true`. When it passes, record `"reach": "ssh <alias>"` for that computer in the ledger, and run its shell chores yourself, with no model turn on that computer, each through that computer's login shell, so its `PATH` and Python are the ones its tasks use: `ssh -o BatchMode=yes <alias> zsh -l <<'EOF'`, then the command on its own lines and `EOF` (on standard input, so it needs no second layer of quotes; on a computer whose shell isn't zsh, its own login form, such as `bash -l`). A command in it that may read its input (`read`, `cat` with no file, `ssh` without `-n`, a test runner) gets `</dev/null`, or it swallows the lines after it and the shell ends early, often with exit 0. Every command below, and every other chore the skill sends over SSH, goes this way:

- **Pre-flight:** every command of section 3, each its own `ssh` call, read straight from its output.
- **Keep-awake and sampler:** started detached, so `ssh` returns at once, and their process IDs recorded in the ledger and in the files section 3 names: `nohup caffeinate -i -t <seconds> </dev/null >/dev/null 2>&1 & echo $!`, then the sampler the same way (`mkdir -p <run directory>/usage && nohup <skill folder there>/scripts/usage-sampler --machine-only <run directory>/usage </dev/null >/dev/null 2>&1 & echo $!`), and `ps -p <pid>` to confirm each.
- **During the run:** `run-watch` and the heartbeat check that computer themselves on every wake, with one `ssh` call that runs its own `run-watch` there (section 8), once `watch.json`'s `"machines"` gives it `"reach": "ssh <alias>"`; this replaces section 8's check threads. When it says `unreachable` because the copy there is older than 5.10.0 and you haven't copied a newer one yet (section 3), check it by hand with one call on the wakes that read a task there: `df -h /System/Volumes/Data; pmset -g batt; ps -p <keep-awake pid>,<sampler pid> -o pid=,command=; ps -axo pid=,comm= | grep " <SecurityAgent's path>$"` ([machine.md](machine.md#7-during-the-run) gives the path), and `ps -axo pid,lstart,command | grep -F <run directory>` for leftovers (the check's own shell and `grep` lines show too: leave them out).
- **The finish:** the finish steps (section 9) as `ssh` calls: the final sample and the sampler's stop, `run-costs` with `--task`, the keep-awake's stop, the leftovers stopped by process ID, the cleanup gate, `KEEP` in unfinished tasks' folders, the fast-forwards, `prune-runs --mark-finished`. With SSH, `share-usage send` isn't needed: `share-usage fetch <run directory> --ssh <name>=<alias>` reads `machine.jsonl` and `costs.json` straight from there, from the same path under that computer's home folder (give `--remote-run <path there>` when its run directory is elsewhere, for example a different `XDG_STATE_HOME`) (add `--state <state repository>` to fetch the other computers from the briefs branch too); a computer SSH can't reach (or whose run directory isn't at that path there) keeps its earlier copies, is named, and makes the fetch exit 1; then the briefs branch is the fallback: have the machine thread below run `share-usage send` there (section 9, step 3), then run the same fetch with `--state` added: a computer SSH couldn't reach is fetched from the branch instead (its earlier copies stay until its files are there), so keep that machine thread until they have arrived.

The same rules hold over SSH as at home: stop only what the run started, by its recorded process ID; delete only with literal paths in a call of their own; nothing that asks for a password (an `ssh` that would prompt fails in batch mode instead, which is the point). A bare `ssh <alias> '<command>'` gets no login shell: its `PATH` lacks Homebrew, so `python3` there may be macOS's own 3.9, older than `run-watch` needs; each of this skill's scripts started on a Python older than it needs stops at once with one line naming that Python and the version it needs (exit 69): run the chore again through the login shell. Only `share-usage fetch --ssh` reads without it, since its remote command is `sh` and `cat` alone, and a login shell's start-up files could add their own output to the bytes it copies. Some checks need the owner's logged-in session there and fail over SSH although they pass on that computer: OpenCode's `opencode api skill.list` is killed over SSH (exit 137), so a check that lists OpenCode's skills (a skills repository's doctor) fails there. Run those through the machine thread, or name them unchecked. SSH can't do what needs the T3 app's own macOS permissions or the owner at that computer: the screen, Accessibility, the keychain, or asking the owner for a secret there. Those go to the machine thread.

**One machine thread, without SSH or for what SSH can't do.** Launch one run-owned thread per other computer at pre-flight (with SSH, only when a chore needs it): `t3_thread_launch` with that computer's `environmentId` and `projectId`, without `workspaceStrategy`, on your home harness at medium reasoning, titled `<run> · machine <computer>`. Record it in the ledger and in `watch.json` under `"machines"`, never under `"tasks"`: `"machines": {"den-mac": {"environmentId": "<id>", "thread": "<thread ID>", "reach": "thread"}}`, or `"reach": "ssh den-mac"` for a computer reached over SSH, whose machine thread, if it has one, does only what SSH can't. Every chore of section 3, 8 and 9 that SSH doesn't do is a message to that thread (`t3_thread_send` with its `environmentId`, mode `queue`), whose reply you read with `t3_thread_read`; it takes this run's chores only, and you settle it at the finish, after its last chore. **Never use the owner's own threads for run chores,** not even one already open on that computer: they are the owner's conversations, and a chore in one changes their history and context.

**When the T3 link is down** (`t3_environment_links` shows that computer not connected, or calls with its `environmentId` fail), and the profile names an alias, SSH is how you find out what happened there (through its login shell, as above):

- whether the computer is up and awake: `uptime`, `pmset -g batt`, and `pmset -g log | grep -E ' (Sleep|Wake) ' | tail -5`;
- whether T3 runs: `ps -axo pid,lstart,command | grep -i '[t]3 code'`;
- what it logged last: the newest files in `~/.t3/userdata/logs/` (`ls -t ~/.t3/userdata/logs | head`, then `tail -50` of the newest), and whether the run's task processes still run (`ps -axo pid,lstart,command | grep -F <run directory>`).

A task that keeps working while only the link is down needs nothing: read its thread once the link is back. Restarting the owner's T3 app is a last resort, for a link that stays down while work waits on it: only when T3 isn't running at all, start it (`open -a "T3 Code"`, over SSH); never quit a running copy over SSH. Record either as an incident in the ledger, with the time and what you saw. Without SSH, a link that stays down is the owner's to fix; park that computer's tasks and say so in the report.
