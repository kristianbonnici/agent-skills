# The run contract

The one message the user approves before the run. SKILL.md ("Present the run contract and get one approval") says how approval works and what happens to decisions that come up later; this file says what the message holds.

Put everything the user might want to decide into one message, so nothing needs asking later:

- **Tasks:** one plain-language line each, with the waves and dependencies.
- **How tasks run:** in T3, each task in a top-level thread of its own, which the user's approval of the contract asks for; elsewhere, as the host's subagents. Say how many tasks run at once at most on this computer, and how many of them may build or run heavy test suites at the same time (the `cpu` lease's slots, [machine.md](machine.md#6-shared-resources-and-disk)). With tasks on another computer, give both limits for each computer, and add the part **Computers** ([computers.md](computers.md#4-in-the-contract)): each computer's role and pre-flight findings, the run branch the tasks push to, and what you can't watch there.
- **Per task:** its computer, when the run uses more than one, with the reason for any not yours (never place a live-UI-required desktop task on a computer with no usable screen); host or provider, model and effort, branch, exclusive resources such as test ports, the helpers it may use, its review level (light, standard or deep, by the `review-gate` skill's rules) with the reviewers that level gives it, and — for every task that changes visible UI — its **Live UI check** classification: `required` by default, or `rendered is enough because <reason>` only when all three hold (every pixel in and next to the changed region is drawn by the project's own code; the state is reachable without input or elapsed time; the render is the shipped view tree, not a fixture, poster or placeholder), or `waived` (only when the owner approves merging without live capture, such as a headless target). A task may upgrade `rendered is enough` to `required`, never downgrade `required`; reviewers verify the classification against the diff. Give the reason for how tasks are placed across peer primary subscriptions (or routed away from them), and for any task above high or on Fable 5.2.
- **Usage:** each subscription's current usage in plain words (for Claude, the Fable week beside the all-models week; for Antigravity, both `gemini_models` and `claude_and_gpt_models` windows), any other active run sharing them ([routing.md](routing.md#2-measure-capacity-as-plan-size-times-room-left) shows how to find them), and what the run is expected to consume. For Claude, estimate it from this run's tasks (by model, review level and your own wakes), never from an earlier run's total, and give the run a budget in points of the all-models week ([routing.md](routing.md#the-runs-claude-estimate-and-budget)). With a task on Fable, give the run's Fable budget in points of the Fable week, and say that a Fable task continues on Opus 5.5 once the budget is used or the Fable week runs out. When your own thread runs on Fable, say what your wakes will cost of the Fable week, so the owner can switch you to Opus 5.5 before they leave. For Antigravity, give the run's `gemini_models_weekly` budget (covering primary Antigravity tasks, Neon reviews, Neon advanced helpers, and Hydrogen) and, when using Antigravity's Claude bucket for reviews or bounded Claude tasks, its `claude_and_gpt_models_weekly` budget and whether `claude_and_gpt_models` is preferred for Claude reviews ([routing.md](routing.md#the-runs-antigravity-budgets)). Say that work pauses on the same thread when a 5-hour window runs out and resumes after its reset (at what time if that is likely), and whether weekly limits or budgets on a peer primary subscription may spill queued or running tasks once to the other peer primary subscription while small plans never absorb primary tasks and your own thread never switches.
- **Another run:** if another orchestrator is active on this computer, what you agreed with it before the contract: the code areas each run stays out of, the shared lease folder (never drop a shared resource such as `screen` to avoid sharing it; going without `screen` for UI tasks is a contract waiver the owner approves), ports and folders, and who does the shared finish steps ([routing.md](routing.md#running-beside-another-orchestrator)).
- **Integration branch:** the branch checked out where the run starts (`main`, `dev`, …).
  - Default policy: each task commits, passes the review gate (the `review-gate` skill: reviewers of another model family, at a level set by what its diff touches), passes the full checks, and fast-forwards the integration branch itself. Nothing is pushed, except the owner's provider profile and skill lessons to their private state repository when they live there ([routing.md](routing.md#6-the-owners-profile)).
  - One exception you may decide during the run: a task that meets its goal but misses one check narrowly may merge with a follow-up task for the miss ([integration.md](integration.md#a-narrow-measured-miss)). Say so in the contract.
  - Alternative the user may choose: leave each task on its reviewed branch for the user to merge.
  - With a task on another computer, tasks merge by a plain push to a run branch on the remote instead, or under "leave on branch" push their task branches; name these pushes, and the briefs branch, for the owner to approve ([computers.md](computers.md#6-commits-travel-through-the-remote)).
- **Blocked:** what makes a task stop without merging. Other tasks continue when one blocks. For a task with `Live UI check: required`, a live capture that can't run (locked screen, capture unavailable, or screen-lease timeout) stops the merge unless the contract waived it: the task reports `ready` with `"live UI check pending"` and the exact scene, and its dependents park by default (or stack on the ready branch when the contract says so — staying `ready` without fast-forwarding integration until every pending prerequisite has merged). Advisory real-screen checks on non-required or waived tasks don't block a merge (unless that check is the task's main deliverable): the task merges on its other checks and lists them under "Couldn't check".
- **Pre-flight items:**
  - uncommitted work the tasks depend on (new worktrees contain only committed work);
  - an integration checkout that isn't clean;
  - missing credentials or services.
- **Permissions and the computer:** the user won't be there to type a password or click Allow, so the run gets everything it may need before they leave. Err on the side of more: an unused permission costs nothing, while a missing one stops a task or leaves a prompt on the screen. Read the current state, then list what's missing of these, from [machine.md](machine.md):
  - admin commands for the user to paste into Terminal once (Developer mode, toolchain licenses, installs);
  - privacy permissions for the harness app and for the app the tasks build or test (Accessibility, Screen Recording, Automation, …);
  - settings for the run (screen lock and Stage Manager off when anything uses the real screen);
  - the user's own things the run must leave as it found them, and the shared resources tasks take turns on (the screen, the GPU);
  - whether the user may still be at the computer (an evening run): then the screen's lease waits until they have been away five minutes, nothing records the screen or plays out loud before that, and their screen lock must not start sooner ([machine.md](machine.md#6-shared-resources-and-disk)).

  Say that you will keep the computer awake for the whole run (`caffeinate` on macOS), and that the warm-up needs the user at the computer for about five minutes right after they approve. Approving the contract approves all of it.
- **Older runs:** run `scripts/prune-runs` (it only lists) and, when finished runs older than a week, of every project on this computer, hold more than about 1 GB beyond their write-ups, say how much, of which projects, and that you will shrink them to their notes, reports and pictures at the start ([machine.md](machine.md#6-shared-resources-and-disk)). A run folder holding a file named `KEEP` at its top is left whole, and so is a task's folder holding one.
- **Estimate:** a rough duration, labelled as an estimate. Agent runs often finish much faster than planned.
- **Ledger:** where the ledger file will be.

Before posting it, ask Fable for a second opinion on the plan when the run's Fable budget has room ([routing.md](routing.md#a-fable-second-opinion-for-your-own-decisions)), and change what its answer convinces you of.
