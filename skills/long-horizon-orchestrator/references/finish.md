# Finish, and when the user comes back

SKILL.md ("Finish") says when the run is finished. Then do these steps in order. With tasks on another computer, read them with [computers.md](computers.md#6-commits-travel-through-the-remote) (section 6, step 4) beside you: the steps below check the run branch, and that computer's finish steps, over SSH or through its machine thread, do its part.

1. Wait for any merged task that is still running to go idle, and finish its cleanup. Then stop the keep-awake (`kill <its recorded process ID>`), close or cancel any remaining agents, and stop the run's leftover processes: test builds, watchers, the kit's browsers, computer-use services the run's steps started, and every virtual machine or container the run created, started or restarted ([machine.md](machine.md#8-leftover-processes)).
2. Verify the end state:
   - the integration branch log;
   - nothing was pushed;
   - the integration checkout is clean;
   - every merged task's worktree, branch, `scratch/` folder and harness temp folders are removed, and its entry and its helper threads tidied (`scripts/prune-runs --harness-temp` with every task's worktree and `<run directory>/<task ID>` lists what is left; remove a merged task's with `--apply`);
   - for each unfinished task with a worktree, save its patch using only steps 1–3 in [integration.md](integration.md#a-task-the-user-stopped) without changing its status, keep its worktree and patch, and put `KEEP` in its run folder; in T3 settle its thread and helpers without touching these;
   - the run directory's size (`scripts/prune-runs --size <run directory>`, whose second line counts the tasks' harness temp folders still left), for the report's closing line.
3. Compare the user's state with the snapshot: restore what the run changed, remove what it left, and note anything you couldn't for the report's "Side effects" ([machine.md](machine.md#5-the-users-own-things)). If another run is still active, leave the steps you share with it to whichever finishes last, as agreed, and tell it you have finished; if it hasn't answered all run, do them yourself, as [routing.md](routing.md#running-beside-another-orchestrator) says.
4. If tasks merged on the cheaper re-check after a clean rebase ([integration.md](integration.md#many-tasks-merging-at-once)), run the project's full check once on the integration branch, and send what it finds to the task that owns it or to a follow-up task; otherwise, if the project has a quick main check, run that once. Run it in a detached worktree (`git worktree add --detach <run directory>/final-check <integration branch>`, then `git worktree remove --force` it, since it holds no work) when another run still works in the checkout, or when the check writes files the user's own copy uses, such as the app they have running.
5. Remove throwaway threads or worktrees you made along the way. With tasks on another computer, run its finish steps now (over SSH, or through its machine thread, [computers.md](computers.md#10-reaching-it-ssh-first-one-machine-thread-second)), which bring that computer's machine samples and costs over and also fast-forward its integration branch, and fast-forward yours, so the report can say how both went (under "leave on branch", neither); keep your run-branch and briefs worktrees (and the state repository's finish clone, [computers.md](computers.md#6-commits-travel-through-the-remote) step 5) until step 10 ([computers.md](computers.md#9-the-ledger-the-finish-and-the-report)).
6. **Skill evolution.** If the `skill-evolution` skill is installed, follow it on this run: the ledger's incidents and the tasks' handoffs. It records every incident in the owner's private lessons (with a state run branch, through the finish clone, [computers.md](computers.md#6-commits-travel-through-the-remote) step 5) and gives you every skill change it proposes, the top three in full and the rest one line each, for the report's "Skill changes proposed"; it changes no skill. Most runs should propose none.
7. Take the final usage snapshot with `<skill folder>/scripts/usage-sampler --final <run directory>/usage` (seconds as a rule, but give the shell call a 5-minute timeout, 300000 where it counts milliseconds), which adds it to the sampler's folder, so every subscription has an end point however short the run, and note it in the ledger; with no folder, or if it fails, use `scripts/provider-usage`. Update the calibration in the owner's provider profile. If the profile lives in the owner's private repository, commit and push it (see [routing.md](routing.md#6-the-owners-profile); when that repository's run branch holds commits its `main` lacks, the profile and lessons go there, as [computers.md](computers.md#6-commits-travel-through-the-remote) step 5 says).
8. Stop the usage sampler (`kill <its recorded process ID>`; it ends within a moment), then write the final report from [final-report.md](final-report.md), with the tasks' pictures of what changed and a picture of how the run actually went: in T3 the run map, shown with `html_render` just before the report; elsewhere its two Mermaid charts (a dependency graph and a timeline). With tasks on another computer, first bring their computers' samples and costs in: `scripts/share-usage fetch <run directory> --state <state repository> --expect <each other computer>`, with `--ssh <name>=<alias>` for a computer reached over SSH ([computers.md](computers.md#9-the-ledger-the-finish-and-the-report)). Before the charts, in T3 (it reads T3 Code's records; elsewhere skip it, and the map shows no costs), set `"finished"` in `watch.json` to now and run `scripts/run-costs <run directory> [--orchestrator <your thread ID>, when watch.json lacks it] --json <run directory>/report/costs.json --markdown <run directory>/report/costs.md`: what the run's tokens would have cost at API list prices, per thread and model, for you, each task, its reviewers and its helpers ([final-report.md](final-report.md#cost-at-api-prices)), with every other computer's `computers/<name>/costs.json` added. `scripts/run-charts` draws all of them from one facts file (with `"costs": {"file": "<run directory>/report/costs.json"}`, each card shows its cost), with the usage graphs from the sampler's folder (`"usage": {"folder": "<run directory>/usage"}`, and with tasks on another computer `"computers"`: each computer's name and role, yours first), the ledger's rounds and the Mac's sleeps (`run-watch`'s `slept` lines in `times.log`); with rounds, pass `--repo <integration checkout>` so it finds what each round's tasks built on. Save a copy next to the ledger, for the record.
9. If you have OrbOS's `offer_reading` tool, offer the report once, as a reading to listen to later with its tour ([final-report.md](final-report.md#offer-it-to-listen-to-with-its-tour)). `scripts/report-offer` turns the facts file and the saved report into the tool's arguments and offers them through OrbOS's own command, so the tour shows the tasks' pictures too; if it can't, it says so and you call `offer_reading` yourself. It returns within moments, and the card waits in the notch for 8 hours, with **Tour** beside **Play**: the user plays the tour whenever they like, without you.
10. In T3, discover this run's helper descendants and check the ledger IDs against `t3_thread_list({settled: false, includeSubagents: true})` as [host-t3.md](host-t3.md#keeping-the-thread-list-honest) says; settle any still listed. Keep your own thread pinned and unsettled. With tasks on another computer, remove your run-branch and briefs worktrees now, and the state finish clone unless it holds unpushed or uncommitted work ([computers.md](computers.md#6-commits-travel-through-the-remote) step 5) ([computers.md](computers.md#6-commits-travel-through-the-remote)). Set the ledger's status to `finished`, then stop the heartbeat, the warm-up wake if it is still there, any resume wake, and any task's review-gate wake still listed (the heartbeat stays until here, so a turn that dies while the report is prepared is woken again).
11. If the host has a push-notification tool, send one line saying the run is finished.
12. **Post the report in the chat as your final message.** This applies to every ending: all tasks merged, some blocked or parked, or the run stopped early. The saved copy isn't enough; the user reads the chat. Nothing comes after it in this turn.

    Without OrbOS's tools, skip step 9 silently, and never speak aloud about it. When the offered reading couldn't keep its tour (an OrbOS that can't, or no offer) and you have OrbOS's `walkthrough` tool, the report's last line says a live tour is available on request ([final-report.md](final-report.md#the-live-tour-only-when-the-tour-didnt-wait)).
13. The report ends the run. Start nothing new after it, even with allowance left: put further work under "What needs you" and wait for the user. A tour they ask for ("walk me through the run") isn't new work: point them to **Tour** on the waiting card, or give it from the same files.

## When the user comes back

The user may answer open decisions, check something themselves, or ask for changes after reading the report. Keep the run's discipline for these:

- **A check the user did counts.** If a task was blocked only on a check the user has now done, record their result and let the task finish its merge gate.
- **Changes go to the task that owns the work.** For an unfinished task, unsettle its T3 thread first, then send the request to its thread. For merged work, launch a small follow-up task. Make a change of a few lines yourself only if that is clearly simpler, and then run the full checks and the merge gate as a task would.
- **A tour when they ask.** "Walk me through the run": while the offered reading waits with its tour, **Tour** on its card plays it. Otherwise give the live tour from `tour.json` ([final-report.md](final-report.md#the-live-tour-only-when-the-tour-didnt-wait)). Run `scripts/report-offer --no-offer` again first if the report or the integration branch changed since, because the file steps' lines are found at its head.
- **Skill changes are the user's to pick.** "Apply L-K7QM" is a follow-up task in the skills repository, briefed with the proposal and the `skill-evolution` skill's "When the owner decides"; "skip L-M3DX" is recorded with its `lessons set`. Only an answer that names a proposal counts: a general "sounds good" applies none.
- **A new round.** Work the user starts after the report is a new round of the same run: add it to the ledger's rounds (what started it, when, the commit it starts from) and close it there when its report goes out, with the commit it ended on, so the run map draws each round under the one before. A round with a task on another computer runs that computer's pre-flight again first, whose new `run.json` drops the last finish's time there ([computers.md](computers.md#3-pre-flight-on-the-other-computer)).
- **Close the loop.** Update the ledger, clean up as the finish does (above), and post the report again: the whole report, updated, with one line at the top saying what changed since the last one. Offer the new reading as in step 9 when the outcome changed. The old card can't be withdrawn from a new session, so it waits until the user dismisses it or it expires.
