# What run-watch prints

`scripts/run-watch` prints one line per finding, and `scripts/heartbeat` passes the same lines on. Each line starts with a word saying what it is. Do what this file says for that word:

A line about another computer, which run-watch checked over SSH, names it after its word and after the task or process it names: `hang B on den-mac: …`, `disk on den-mac: …`. A one-time line from there (a `hog`, a `blind`, a first `vm` or `leftover` line, a `slept`, a `commit` or `report`, a disk fall) that a lost result carried comes on a later wake instead, beside that wake's own lines (a leftover's "still running" too), with that computer's times in it. Its process IDs and paths are that computer's: run every command below for it there, over SSH through its login shell ([computers.md](computers.md#10-reaching-it-ssh-first-one-machine-thread-second)), never on yours, and tell its task through its thread with that computer's `environmentId`.

- `hang`: a running task's tool call with no result for over 6 minutes whose own processes used no CPU, started nothing and wrote nothing meanwhile. Idle isn't proof it is stuck. Stop it only when you can name what it waits on and why that won't answer: a read of a pipe whose other end only the harness holds, which never writes to a command's input (`lsof -p <pid> -d 0,1,2` shows the pipe; `lsof -nP | grep <its device or node>` shows who holds the other end), or a stack parked in a wait the run already knows stalls, such as a stalled system service (`sample <pid> 1`, which leaves its report in `/tmp`). A wait on another of the task's processes, or one you can't explain, isn't enough. Then stop it by the process IDs it names (check each with `ps -p <pid> -o command=` first) and tell the task what hung and how to avoid it. Otherwise tell the task (in T3, `t3_thread_send` in mode `steer`) what looks stuck and let it decide. When it names no process to stop, another call started within a minute of it and may own some of those processes: find which one is stuck first.
- `idle`: idle now, with nothing written or started for 6 minutes, but not shown idle all that time, or holding a network connection, so it may still be working. Look at the call and its thread, and don't stop it yet: a later wake says `hang` once it is shown idle. One still `idle` after 20 minutes is probably stuck: decide with the task.
- `approval`: a shell call with no process running for it, which is an approval prompt (or a hang before the command started). Clear it as step 2 of "On every wake" in SKILL.md says: interrupt the turn and tell the task how to finish without that command.
- `quiet`: a running task whose session log, worktree and run folder haven't changed for 20 minutes. Read its thread: it may be waiting on reviewers, stuck, or done without reporting.
- `hog`: a process started since the run began, not the run's, above 80% of a core for 10 minutes (such as a system service a task's tests set off). Don't stop it. Find what drives it, tell the tasks, and note it.
- `disk`, `swap`, `dialog`, `keep-awake`, `sampler`: free disk falling 10 GB in 5 minutes or below 20 GB (naming the running tasks' folder that grew most, a harness temp folder too), swap above 20 GB, a password dialog, a stopped keep-awake or sampler. Act as step 4 of "On every wake" in SKILL.md says.
- `vm`: a virtual machine started since the run began, with its memory (later wakes: "still running"). Note which task uses it; the finish stops it.
- `slept`: the Mac slept (a sleep something asked for passes `caffeinate -i`), and tasks ran only in dark wakes: tell the tasks whose timings it skewed, and keep the span for the report's facts (`asleep`). `slept <from> -` means this wake is itself a dark wake.
- `commit`, `merged`, `report`: the exact times of a task's commits, merges and report-backs. run-watch also adds them to `<run directory>/times.log`; take the ledger's times from there or from the integration branch's `git reflog --date=iso`, never from memory.
- `leftover` (another computer only): a process started since the run began that names the run directory there or works in a task's folders, and isn't a running task's, the keep-awake's or the sampler's: a merged or stopped task's build, watcher or service. Check it with `ps -p <pid> -o command=` there, and stop it by its process ID once nothing of the run needs it, as [machine.md](machine.md#8-leftover-processes) says. Later wakes say "still running", which the heartbeat keeps in its summary.
- `unreachable`: the SSH check of another computer gave nothing this wake, for the reason it names (ssh failed or timed out, no run directory or no copy of `run-watch` there, a copy older than 5.10.0, an old Python, `run-watch` there out of its time because something it runs there hangs, such as `pmset`, `lsof`, `git` or `du`, or the alias reached another computer). Its running tasks are `blind` until it answers again: read their threads, and fix what it names (a copy too old: [computers.md](computers.md#3-pre-flight-on-the-other-computer)). If it lasts, check that computer through its machine thread ([computers.md](computers.md#8-watching-it)).
- `note on <computer>: ssh … brought run-watch's result but didn't end`: the check worked and its lines are above, but the session stayed open until the time limit, so every wake waits the whole 90 seconds: something that computer's login files start (a background job that keeps the session's output) holds it open. Find it there and fix it, or give `"shell"` in its `"machines"` entry a login form that doesn't start it.
- `blind`, `note`: it reads Claude Code and Codex session logs; for tasks on other harnesses it sees only processes and files, so keep reading their threads. A task whose `computer` in `watch.json` isn't yours is read by that computer's own `run-watch` when `watch.json`'s `"machines"` reaches it over SSH, and is then watched like one of yours; without SSH, or on a wake its computer was `unreachable`, it is `blind`: run-watch reads nothing of it, and you read its thread on every wake with its `environmentId` ([computers.md](computers.md#8-watching-it)).
