# What run-watch prints

`scripts/run-watch` prints one line per finding, and `scripts/heartbeat` passes the same lines on. When `heartbeat` or `watch-wait` runs it, local one-time findings (`settings`, `hog`, `blind`, `commit`, `merged`, `report`, first `vm`/`leftover`, disk fall, completed sleep) stay pending in `run-watch.state.json` (`local_once`) until printed and acknowledged (`--ack-once`), so stopping a watcher never drops them; an ack timeout or an overlapping manual `run-watch` can replay a pending one-time line once more. Each line starts with a word saying what it is. Do what this file says for that word:

A line about another computer, which run-watch checked over SSH, names it after its word and after the task or process it names: `hang B on den-mac: …`, `disk on den-mac: …`. A one-time line from there (a `hog`, a `blind`, a first `vm` or `leftover` line, a `slept`, a `commit` or `report`, a disk fall) that a lost result carried comes on a later wake instead, beside that wake's own lines (a leftover's "still running" too), with that computer's times in it. Its process IDs and paths are that computer's: run every command below for it there, over SSH through its login shell ([computers.md](computers.md#10-reaching-it-ssh-first-one-machine-thread-second)), never on yours, and tell its task through its thread with that computer's `environmentId`.

- `hang`: (Claude Code and Codex only) a running task's tool call with no result for over 6 minutes whose own processes used no CPU, started nothing and wrote nothing meanwhile. Idle isn't proof it is stuck. Stop it only when you can name what it waits on and why that won't answer: a read of a pipe whose other end only the harness holds, which never writes to a command's input (`lsof -p <pid> -d 0,1,2` shows the pipe; `lsof -nP | grep <its device or node>` shows who holds the other end), or a stack parked in a wait the run already knows stalls, such as a stalled system service (`sample <pid> 1`, which leaves its report in `/tmp`). A wait on another of the task's processes, or one you can't explain, isn't enough. Then stop it by the process IDs it names (check each with `ps -p <pid> -o command=` first) and tell the task what hung and how to avoid it. Otherwise tell the task (in T3, `t3_thread_send` in mode `steer`) what looks stuck and let it decide. When it names no process to stop, another call started within a minute of it and may own some of those processes: find which one is stuck first.
- `idle`: (Claude Code and Codex only) idle now, with nothing written or started for 6 minutes, but not shown idle all that time, or holding a network connection, so it may still be working. Look at the call and its thread, and don't stop it yet: a later wake says `hang` once it is shown idle. One still `idle` after 20 minutes is probably stuck: decide with the task.
- `approval`: (Claude Code and Codex only) a shell call with no process running for it, which is an approval prompt (or a hang before the command started). Clear it as step 2 of "On every wake" in SKILL.md says: interrupt the turn and tell the task how to finish without that command. (Antigravity conversation DBs do not expose open tool calls or approval prompts reliably, so in T3 the heartbeat's `approval-task` line catches them, and `quiet` after 20 minutes.)
- `quiet`: a running task whose session log (or Antigravity conversation `.db` and `.db-wal`), worktree and run folder haven't changed for 20 minutes. Read its thread: it may be waiting on reviewers, stuck, or done without reporting.
- `hog`: a process started since the run began, not the run's, above 80% of a core for 10 minutes (such as a system service a task's tests set off). Don't stop it. Find what drives it, tell the tasks, and note it.
- `disk`, `swap`, `dialog`, `keep-awake`, `sampler`: free disk falling 10 GB in 5 minutes or below 20 GB (naming the running tasks' folder that grew most, a harness temp folder too), swap above 20 GB, a password dialog, a stopped keep-awake or sampler. Act as step 4 of "On every wake" in SKILL.md says.
- `vm`: a virtual machine started since the run began, with its memory (later wakes: "still running"). Note which task uses it; the finish stops it.
- `slept`: the Mac slept (a sleep something asked for passes `caffeinate -i`), and tasks ran only in dark wakes: tell the tasks whose timings it skewed, and keep the span for the report's facts (`asleep`). `slept <from> -` means this wake is itself a dark wake.
- `commit`, `merged`, `report`: the exact times of a task's commits, merges and report-backs. `run-watch` also adds them to `<run directory>/times.log`; take the ledger's times from there or from the integration branch's `git reflog --date=iso`, never from memory. `merged` and `report` are actionable and wake immediately; `commit` lines alone keep `scripts/heartbeat` at `nothing to act on` (still noted in its summary/ledger line) and do not wake `scripts/watch-wait` — both scripts buffer seen `commit` lines and print them alongside the next real wake.
- `usage:` (heartbeat and `watch-wait`): a window that crossed a mark in `watch.json`'s `"usage_marks"`, a built-in `five_hour >= 85%` threshold, or the built-in `>= 95%` threshold (or a failed/empty live reading). Once a per-window warning has been delivered, repeated unchanged readings for that window are suppressed until it resets, recovers below its threshold, or crosses a new threshold or mark (including `>= 95%` on first crossing); the summary line always shows current percentages so recovery stays visible.
- `settings <domain>: <key> <old>→<new>`: a key of the owner's settings changed since its snapshot (`owner_defaults` in `watch.json`; `<changed>` hides a long, structured or secret-looking value). Find the build that wrote it: restore what a test build changed at once, that key alone (`defaults write` or `defaults delete`; never import the whole snapshot), and tell its task (or the other run whose build did it). A key the owner's own running copy writes in normal use is theirs: note it, leave it, and add it to that entry's `"ignore"`. Each new value is said once.
- `next-run <thread>`: the run waiting to start after this one can start ([routing.md](routing.md#running-beside-another-orchestrator)). Send its thread the start message, record it in the ledger, and set `"started"` in `watch.json`'s `"next_run"`.
- `watcher`: `scripts/watch-wait` isn't running though `watch.json` has `"watcher"`: start it again as the host reference says.
- `approval-task`, `approval-subagent` (heartbeat only, from T3's own records): a request waits on that task's thread, or on a reviewer's or helper's thread under it. For a subagent, tell the task to stop it with `task_cancel` and relaunch it once ([host-t3.md](host-t3.md#heartbeat-a-backup-for-silent-tasks)); for the task's own thread, interrupt the turn and tell it how to finish without that command. Note each thread in the ledger and say nothing twice.
- `t3-state unreadable` (heartbeat only): T3's database couldn't be read, so read the running tasks' subagents with the tools this wake, as host-t3.md says; the summary's "read with the tools on <computer>" asks the same for that computer's tasks.
- `leftover` (another computer only): a process started since the run began that names the run directory there or works in a task's folders, and isn't a running task's, the keep-awake's or the sampler's: a merged or stopped task's build, watcher or service. Check it with `ps -p <pid> -o command=` there, and stop it by its process ID once nothing of the run needs it, as [machine.md](machine.md#8-leftover-processes) says. Later wakes say "still running", which the heartbeat keeps in its summary.
- `unreachable`: the SSH check of another computer gave nothing this wake, for the reason it names (ssh failed or timed out, no run directory or no copy of `run-watch` there, a copy older than 5.10.0, an old Python, `run-watch` there out of its time because something it runs there hangs, such as `pmset`, `lsof`, `git` or `du`, or the alias reached another computer). Its running tasks are `blind` until it answers again: read their threads, and fix what it names (a copy too old: [computers.md](computers.md#3-pre-flight-on-the-other-computer)). If it lasts, check that computer through its machine thread ([computers.md](computers.md#8-watching-it)).
- `note on <computer>: ssh … brought run-watch's result but didn't end`: the check worked and its lines are above, but the session stayed open until the time limit, so every wake waits the whole 90 seconds: something that computer's login files start (a background job that keeps the session's output) holds it open. Find it there and fix it, or give `"shell"` in its `"machines"` entry a login form that doesn't start it.
- `blind`, `note`: it reads Claude Code and Codex session logs, and tracks Antigravity conversation DBs (`.db` and `.db-wal`, mapped via `session_log`, `session`, or `thread` in T3's `statev2.sqlite`) for activity and `quiet` so Antigravity tasks whose DB is found leave `blind`. Antigravity DBs use binary protobufs without reliable open-call or approval fields, so `run-watch` does not emit `hang`, `idle`, `approval`, or `report` for Antigravity tasks: approval waits on Antigravity rely on the heartbeat's `approval-task` line (plus `quiet` at 20 minutes), and report-backs arrive via `t3_thread_send`. For tasks on other harnesses, or Antigravity tasks whose DB isn't found yet, it sees only processes and files, so keep reading their threads. A task whose `computer` in `watch.json` isn't yours is read by that computer's own `run-watch` when `watch.json`'s `"machines"` reaches it over SSH, and is then watched like one of yours; without SSH, or on a wake its computer was `unreachable`, it is `blind`: run-watch reads nothing of it, and you read its thread on every wake with its `environmentId` ([computers.md](computers.md#8-watching-it)).
